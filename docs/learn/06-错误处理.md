## 跑起来看什么

这次打开持久化启动服务端（不写 `-aof`，默认就是 `data/appendonly.aof`）：

```text
go run ./cmd/server
```

用客户端执行：

```text
mini-redis> SET a 1
OK
mini-redis> LPUSH l x y
(integer) 2
mini-redis> EXPIRE a 100
(integer) 1
mini-redis> DEL nothing
(integer) 0
mini-redis> SET a 2
OK
```

按 Ctrl+C 停掉服务端，看看 `data/appendonly.aof` 里写了什么。文件里的记录是首尾相连的，共 140 字节；为了好读，下面每条记录占一行，`\r\n` 代表回车、换行两个字节：

```text
*3\r\n$3\r\nSET\r\n$1\r\na\r\n$1\r\n1\r\n
*4\r\n$5\r\n_LNEW\r\n$1\r\nl\r\n$1\r\nx\r\n$1\r\ny\r\n
*3\r\n$12\r\n__EXPIREATMS\r\n$1\r\na\r\n$13\r\n1794366172939\r\n
*3\r\n$3\r\nSET\r\n$1\r\na\r\n$1\r\n2\r\n
```

文件里是一条一条的 RESP 请求，格式和客户端发来的一样。但仔细看，记下的并不完全是你输入的命令：

- `LPUSH l x y` 记成了 `_LNEW`：这是一个新建的列表。
- `EXPIRE a 100` 记成了 `__EXPIREATMS`，后面跟的是**到期时刻**的毫秒时间戳，而不是“100 秒”。
- `DEL nothing` 没有被记下来：它什么也没删，不需要重放。

为什么这样记，见本章的“关键设计”。再次启动服务端，数据都回来了：

```text
mini-redis> GET a
"2"
mini-redis> LRANGE l 0 -1
1) "y"
2) "x"
mini-redis> TTL a
(integer) -1
```

`TTL a` 是 -1：最后那条 `SET a 2` 覆盖值时清掉了期限，重放时也一样。

## Go 基础

### 1. error 是一个接口

```go
type error interface {
	Error() string
}
```

任何有 `Error() string` 方法的类型都是 error。Go 的惯例是：可能失败的函数，把 error 作为**最后一个返回值**；调用者拿到以后立刻检查。

```go
data, err := os.ReadFile(path)
if err != nil {
	return fmt.Errorf("read config: %w", err)
}
```

### 2. 创建、包装和判断错误

```go
package main

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
)

// 哨兵错误：包级的错误变量，调用者用 errors.Is 判断“是不是这个错误”。
var ErrNotFound = errors.New("not found")

// 自定义错误类型：需要携带额外信息时用。
type ParseError struct {
	Offset int64
	Err    error
}

func (e *ParseError) Error() string { return fmt.Sprintf("parse at byte %d: %v", e.Offset, e.Err) }
func (e *ParseError) Unwrap() error { return e.Err } // 让 errors.Is/As 能看到里面的错误

func find(key string) error {
	return fmt.Errorf("find %q: %w", key, ErrNotFound) // %w 包装：保留原错误
}

func main() {
	err := find("k")
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrNotFound)) // 沿着包装链往里找

	flat := fmt.Errorf("find: %v", ErrNotFound) // %v 只拼进了文字，链断了
	fmt.Println(errors.Is(flat, ErrNotFound))

	var perr error = fmt.Errorf("open AOF: %w", &ParseError{Offset: 42, Err: ErrNotFound})
	var pe *ParseError
	if errors.As(perr, &pe) { // 按类型找，并把找到的错误赋给 pe
		fmt.Println("offset =", pe.Offset)
	}
	if pe2, ok := errors.AsType[*ParseError](perr); ok { // Go 1.26 起的泛型写法，不用先声明变量
		fmt.Println("offset =", pe2.Offset)
	}
	fmt.Println(errors.Is(perr, ErrNotFound)) // 两层包装也能找到

	_, err = os.Open("no-such-file")
	fmt.Println(errors.Is(err, fs.ErrNotExist)) // 标准库的错误也这样判断
}

// 输出：
// find "k": not found
// true
// false
// offset = 42
// offset = 42
// true
// true
```

### 3. 合并多个错误：errors.Join

Go 1.20 起，`errors.Join` 可以把几个错误合成一个，`errors.Is` 会逐个检查。nil 会被跳过，全是 nil 时返回 nil，所以可以放心地把“可能出错的收尾操作”都 Join 进去。

```go
package main

import (
	"errors"
	"fmt"
)

var (
	ErrWrite = errors.New("write failed")
	ErrClose = errors.New("close failed")
)

func main() {
	err := errors.Join(ErrWrite, nil, ErrClose)
	fmt.Println(err) // 每个错误一行
	fmt.Println(errors.Is(err, ErrWrite), errors.Is(err, ErrClose))
	fmt.Println(errors.Join(nil, nil) == nil)
}

// 输出：
// write failed
// close failed
// true true
// true
```

`fmt.Errorf` 也可以写多个 `%w`（Go 1.20 起），效果类似。

### 4. panic 和 recover

```go
package main

import "fmt"

// 把 panic 转成 error：recover 必须写在 defer 的函数里，用命名返回值把错误带出去。
func safeDivide(a, b int) (result int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	return a / b, nil
}

func main() {
	fmt.Println(safeDivide(6, 3))
	fmt.Println(safeDivide(1, 0))

	defer func() {
		fmt.Printf("%T\n", recover()) // Go 1.21 起，panic(nil) 会变成 *runtime.PanicNilError
	}()
	panic(nil)
}

// 输出：
// 2 <nil>
// 0 recovered: runtime error: integer divide by zero
// *runtime.PanicNilError
```

### 5. 只在某些平台编译的代码

两种方式，可以同时用：
- **文件名后缀**：文件名以 `_windows.go`、`_linux.go`、`_darwin.go` 这类“下划线加操作系统名”结尾，就只在那个系统上编译。只认 Go 已知的操作系统和 CPU 架构名。
- **构建约束**：文件开头写 `//go:build linux || darwin`，和 `package` 之间空一行。可以用 `&&`、`||`、`!` 组合。

同一个函数在不同平台上各有一个实现，每个平台都必须恰好有一个，否则在那个平台上会编译失败。Mini-Redis 的 aof 包里，`lockFile` 有三个版本：

| 文件 | 靠什么限定平台 | 实现 |
|---|---|---|
| [lock_unix.go](../../aof/lock_unix.go) | `//go:build linux \|\| darwin` | `unix.Flock` |
| [lock_windows.go](../../aof/lock_windows.go) | 文件名后缀 `_windows` | `windows.LockFileEx` |
| [lock_other.go](../../aof/lock_other.go) | `//go:build !linux && !darwin && !windows` | 返回“本平台不支持 AOF 文件锁”的错误 |

注意 `lock_unix.go` 的文件名里虽然有 `unix`，但 `unix` 不是一个操作系统名，文件名后缀对它不起作用，真正限定平台的是第一行的 `//go:build`。三个文件的条件合起来正好覆盖所有平台，每个平台恰好一个。

早期的版本只有 `lock_linux.go` 和 `lock_windows.go`，在 macOS 上编译直接报 `undefined: lockFile`。检查所有平台都能编译，不需要真的有那台机器：`GOOS=darwin go vet ./...`。现在 CI 里就有这一步。

## 代码走读

### 1. 写入：先日志，后内存

[database/write.go](../../database/write.go) 的 `executeWrite`，去掉加锁部分：

```go
plan, err := e.planWrite(args, cmd, now)
if err != nil || plan.apply == nil {
	return plan.reply, err
}
if e.log != nil {
	if err := e.log.Append(plan.record); err != nil {
		return nil, &commandError{code: "ERR", message: "persistence write failed", cause: err}
	}
}
plan.apply()
return plan.reply, nil
```

- `planWrite` 只计算、不修改：要回复什么、日志记什么、内存怎么改（`apply` 闭包）。参数错、类型错，在这一步就返回，什么都没发生。
- `plan.apply == nil` 表示这次写没有效果（比如 DEL 一个不存在的 key），不写日志，直接回复。
- `Append` 失败：直接返回错误，`apply` 根本不会执行，内存里还是旧值。返回的错误把内部原因放在 `cause` 里，客户端只看到 `persistence write failed`。
- `Append` 成功才 `apply`。所以客户端收到 OK 的写入，一定已经落盘。

### 2. Append 和 fail：写失败以后不再写

[aof/store.go](../../aof/store.go)：

```go
func (s *Store) Append(args [][]byte) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.closed {
		return os.ErrClosed
	}
	if s.failed != nil {
		return s.failed
	}
	data, err := resp.AppendRequest(nil, args)
	if err != nil {
		return err
	}
	size := len(data)
	for len(data) > 0 {
		n, err := s.file.Write(data)
		if err != nil {
			return s.fail(err)
		}
		if n == 0 {
			return s.fail(io.ErrShortWrite)
		}
		data = data[n:]
	}
	if err := s.file.Sync(); err != nil {
		return s.fail(err)
	}
	s.size += int64(size)
	return nil
}

func (s *Store) fail(cause error) error {
	truncateErr := s.file.Truncate(s.size)
	syncErr := s.file.Sync()
	s.failed = fmt.Errorf("append AOF: %w", errors.Join(cause, truncateErr, syncErr))
	log.Printf("AOF persistence failure: %v", s.failed)
	return s.failed
}
```

- `s.size` 是“最后一次确认成功时文件的长度”。只有 write 和 Sync 都成功，它才往前走。
- 编码失败（参数太多、太长）发生在碰文件之前，直接返回，不算故障。
- 写入或 Sync 失败，交给 `fail`：截断回 `s.size`，去掉可能写了一半的记录；再 Sync 一次；把三个错误 `errors.Join` 到一起，存进 `s.failed`。`errors.Join` 会跳过 nil，截断和 Sync 都成功时，合并结果里只有原始错误。
- 从此以后，`Append` 一进来就返回 `s.failed`。这就是八股 4 说的“fsync 失败后不能重试”。
- `fail` 里打了一条日志，同时又返回错误，看起来违反了“错误只处理一次”。这是有意的：引擎只会给客户端回一句笼统的 `persistence write failed`，错误链里的磁盘原因没有人会打印出来。不在这里记下，运维就看不到真正的原因。

### 3. Open：读一条、重放一条

```go
reader := bufio.NewReader(file)
var offset, recovered int64
for {
	if err := ctx.Err(); err != nil {
		return nil, err
	}
	args, size, readErr := resp.ReadRequest(reader)
	if readErr == io.EOF {
		break
	}
	if readErr != nil {
		if !errors.Is(readErr, io.EOF) && !errors.Is(readErr, io.ErrUnexpectedEOF) {
			return nil, fmt.Errorf("invalid AOF at byte %d: %w", offset, readErr)
		}
		if err := file.Truncate(offset); err != nil {
			return nil, fmt.Errorf("truncate AOF tail: %w", err)
		}
		if err := file.Sync(); err != nil {
			return nil, fmt.Errorf("sync AOF recovery: %w", err)
		}
		recovered = info.Size() - offset
		break
	}
	if err := replay(args); err != nil {
		return nil, fmt.Errorf("replay AOF at byte %d: %w", offset, err)
	}
	offset += int64(size)
}
```

三种结果，用三种错误判断区分开：

| `ReadRequest` 返回 | 怎样判断 | 意思 | 处理 |
|---|---|---|---|
| 恰好是 `io.EOF` | `readErr == io.EOF` | 一条记录刚好结束，文件读完了 | 正常结束 |
| 包装过的 EOF 或 UnexpectedEOF | `errors.Is` | 文件末尾有半条记录 | 截断到 `offset`，Sync，继续启动 |
| 其他错误 | 都不是 | 一条完整的记录格式不对 | 拒绝启动，报出出错的字节位置 |

- 第一种用 `==`，第二种用 `errors.Is`，这不是笔误。`ReadRequest` 只在“一个字节都没读到”时原样返回 `io.EOF`，读到一半断开时返回的是包装过的错误。`==` 只认原样的那一个，`errors.Is` 会沿着包装链找。
- `offset` 每重放成功一条，就加上这条记录的实际字节数 `size`。截断时用的就是它。
- 每条记录之前检查一次 ctx：启动时按了 Ctrl+C，恢复可以中途停下。

开头还有一段收尾的写法：

```go
func Open(ctx context.Context, path string, replay func([][]byte) error) (store *Store, err error) {
	// ……打开文件
	defer func() {
		if err != nil {
			err = errors.Join(err, file.Close())
		}
	}()
```

用命名返回值 `err`，defer 里就能看到函数最后返回的是不是错误。出错时关闭文件，并且把关闭的错误也 Join 进去，两个错误都不会丢。成功时不关，文件交给 Store。

### 4. 公开的错误和内部的原因

[database/errors.go](../../database/errors.go)：

```go
type commandError struct {
	code, message string
	cause         error
}

func (e *commandError) Error() string { return e.code + " " + e.message }
func (e *commandError) Unwrap() error { return e.cause }
func (e *commandError) RESPError() (string, string) { return e.code, e.message }
```

[resp/reply.go](../../resp/reply.go) 的 `EncodeReply`：

```go
if execErr != nil {
	var public publicError
	if errors.As(execErr, &public) {
		code, message := public.RESPError()
		if validErrorCode(code) {
			message = strings.NewReplacer("\r", " ", "\n", " ").Replace(message)
			return []byte("-" + code + " " + message + "\r\n"), nil
		}
	}
	return []byte("-ERR internal server error\r\n"), nil
}
```

- `errors.As` 的目标是一个**接口**类型的变量 `public`：在错误链上找“有 `RESPError` 方法的错误”。
- 找到了，也只发 code 和 message，`cause` 永远不出现在回复里；还要检查错误码只含大写字母、把消息里的换行换成空格，防止一条错误回复里夹带出第二条 RESP 回复。
- 找不到，一律回复 `internal server error`。

## Go 八股

### 八股 1：Go 为什么没有 try/catch？

#### 一分钟口述版

> Go 把错误当作普通的返回值，而不是异常。理由是：错误是程序正常流程的一部分，文件可能不存在，网络可能断开，这些都是可以预料的情况，应该在发生的地方就地处理，而不是抛出去，让不知道在哪一层的 catch 去接。返回值的写法让每个可能失败的地方都在代码里一目了然，读代码时能清楚地看到哪里会失败、失败后怎么办。代价是要写很多 `if err != nil`。Go 也有 panic 和 recover，但它们是给真正不该发生的情况用的，比如程序有 bug、数组越界，不是用来做普通的错误处理。处理错误时有三种选择：就地处理掉；加上上下文用 `%w` 包装后返回给调用者；或者记录日志后继续。一个错误只处理一次，不要既记日志又返回，那样日志里会出现重复的记录。

#### 要点

- **错误是值**：可以存起来、比较、包装、合并，不需要特殊的语法。
- **加上下文再返回**：`fmt.Errorf("open AOF: %w", err)`。一层层包装下来，最终的错误信息读起来像一条调用链：`open AOF: lock AOF: resource temporarily unavailable`。
- **只处理一次**：要么返回，要么记录，不要都做。
- **错误信息的写法**：小写开头，不加句号，因为它经常被拼在别的信息后面。

#### 项目里的例子

- [aof/store.go](../../aof/store.go) 的 `Open`，每一步失败都包装上“在做什么”：`open AOF: %w`、`lock AOF: %w`、`invalid AOF at byte %d: %w`、`truncate AOF tail: %w`、`replay AOF at byte %d: %w`。启动失败时，看错误信息就知道卡在了哪一步、文件的哪个位置。动手实验里的 `lock AOF: The process cannot access the file...` 就是这样一条。
- 让进程退出的只有 [cmd/server/main.go](../../cmd/server/main.go) 的 `log.Fatal`。下面各层大多只包装和返回。有两处例外是有意的：AOF 写入失败时 `Store.fail` 记一条日志（代码走读 2 解释了原因）；连接循环里回复编码失败时记一条日志，因为那里已经没有调用者可以返回了。

#### 常见追问

**追问：`if err != nil` 太啰嗦了，有没有办法简化？**

Go 团队讨论过多种新语法提案，最后都没有采纳，官方在 2025 年表示暂时不再推进这类语法改动。实际写代码时，可以把一串可能失败的步骤放进一个小函数，或者用“记住第一个错误”的写法（比如 `bufio.Writer` 出错后，后续写入都直接返回同一个错误，最后检查一次就行）。Mini-Redis 的 AOF Store 也用了类似的思路，见八股 4。

### 八股 2：errors.Is 和 errors.As 有什么区别？

#### 一分钟口述版

> 两者都会沿着错误链往里找，链是通过 Unwrap 方法连起来的，`fmt.Errorf` 用 `%w` 包装时会自动实现 Unwrap，`%v` 只把文字拼进去，链就断了。区别在于找什么：errors.Is 判断链上有没有**某一个特定的错误值**，比如 `io.EOF`、`fs.ErrNotExist` 这种哨兵错误；errors.As 判断链上有没有**某一种类型**的错误，找到了就把它取出来，这样就能读里面的字段，比如取出 `*fs.PathError` 读出路径。Go 1.26 又加了泛型版本的 `errors.AsType`，不用先声明一个变量再传指针。所以设计上：调用者只需要知道“是不是这种情况”，就定义哨兵错误；调用者还需要更多信息，就定义错误类型。不要用比较错误字符串的方式判断错误，字符串随时可能改。

#### 要点

| | `errors.Is(err, target)` | `errors.As(err, &target)` / `errors.AsType[T](err)` |
|---|---|---|
| 找什么 | 一个特定的错误**值** | 一种错误**类型** |
| 怎样算匹配 | `==` 相等，或者链上某个错误的 `Is(target) bool` 方法返回 true | 类型断言成功，或者链上某个错误的 `As(any) bool` 方法返回 true |
| 适合 | 哨兵错误：`io.EOF`、`fs.ErrNotExist`、`context.Canceled` | 需要读取字段的错误：`*fs.PathError`、`*net.OpError` |

- **链怎样连起来**：错误类型实现 `Unwrap() error`（一个）或者 `Unwrap() []error`（多个，`errors.Join` 和多个 `%w` 用的就是这种）。有多个时，按深度优先的顺序查找。
- **`%w` 意味着承诺**：用 `%w` 包装，等于把内部错误当作你的 API 的一部分公开给调用者，以后不能随便换。只想在信息里提一下、不想让调用者依赖它，就用 `%v`。

#### 项目里的例子

**一个错误，两种用途。** `database/errors.go` 的 `commandError` 有三个字段：

| 字段 | 用途 | 谁能看到 |
|---|---|---|
| `code` | 错误码，比如 `ERR`、`WRONGTYPE` | 客户端 |
| `message` | 给客户端看的消息 | 客户端 |
| `cause` | 内部原因，比如磁盘写入失败的具体系统错误 | 只有服务端，通过 `Unwrap` 让 `errors.Is` 能找到 |

- 它实现了 `RESPError() (code, message string)` 方法。[resp/reply.go](../../resp/reply.go) 的 `EncodeReply` 用 `errors.As` 在错误链上找“有这个方法的错误”（接口 `publicError`），找到了就只把 code 和 message 发给客户端；找不到，就统一回复一个通用的错误，不暴露任何内部信息。
- 为什么要这样分开：内部原因里可能有文件路径、系统错误码这些细节，不应该发给客户端。磁盘写入失败时，客户端只会看到 `-ERR persistence write failed`，服务端的日志里有完整的原因。
- **哨兵错误**：`ErrTypeMismatch`、`ErrUnknownCmd`、`ErrInvalidInteger` 都是包级变量。参数个数错误每次的消息都不一样（要带上命令名），所以 `wrongArgs` 每次新建一个 commandError，但把 `ErrWrongArgsNum` 放在 cause 里，测试仍然可以用 `errors.Is(err, ErrWrongArgsNum)` 判断，不用比较字符串。

#### 常见追问

**追问：errors.As 的第二个参数为什么要传指针的指针，比如 `&pe`，而 pe 本身是 `*ParseError`？**

As 要把找到的错误**写进**你的变量，所以需要变量的地址。变量的类型是 `*ParseError`，它的地址就是 `**ParseError`。传错了类型会 panic，`go vet` 能检查出来。`errors.AsType` 用返回值代替了这个参数，就没有这个坑了。

### 八股 3：什么时候该用 panic？recover 能接住所有 panic 吗？

#### 一分钟口述版

> panic 用在“程序本身出了问题、继续运行没有意义”的情况：违反了不该被违反的前提，比如数组越界、空指针；或者初始化时的配置错误，程序根本没法启动。可以预料的失败，比如文件不存在、网络超时、用户输入非法，都应该返回 error。recover 只能在 defer 的函数里直接调用才有效，而且只能接住同一个 goroutine 里的 panic。有几类错误 recover 接不住，它们叫 fatal error，比如 map 并发读写、所有 goroutine 都在等待的死锁、栈溢出、内存耗尽，运行时认为这时程序的状态已经不可信，直接终止。还有一个小细节：Go 1.21 起，`panic(nil)` 会被转换成 `*runtime.PanicNilError`，recover 拿到的不再是 nil，以前用 `recover() != nil` 判断有没有 panic 的代码就不会漏掉它了。

#### 要点

**适合 panic 的情况：**
- 程序员的错误，违反了函数的前提条件。例如 `NewEngine(shardCount)` 要求分片数是 2 的幂，传 3 进来说明调用代码写错了，直接 panic，在测试里就能发现。
- 初始化失败，程序没法启动。例如 `regexp.MustCompile` 用一个写死在代码里的正则，编译失败就 panic。

**recover 的限制：**

| 情况 | 能 recover 吗 |
|---|---|
| 同一个 goroutine、defer 的函数里**直接**调用 | 能 |
| defer 的函数里，再调用一个辅助函数去 recover | 不能 |
| 别的 goroutine 里的 panic | 不能 |
| fatal error：map 并发读写、死锁、栈溢出、内存耗尽、解锁没上锁的 Mutex | 不能 |

**panic 时 defer 仍然会执行**，所以用 defer 释放的锁、关闭的文件，在 panic 时也会被释放和关闭。

#### 项目里的例子

- [database/engine.go](../../database/engine.go) 的 `NewEngine` 在分片数不是 2 的幂时 panic：路由用的是 `hash & (N-1)`，只有 N 是 2 的幂时才等价于取模。分片数是写在代码里的常量（服务端用 16），传错了说明代码写错了，不是运行时的情况。第 00 章的动手实验 3 亲眼看过这个 panic。
- 连接处理的 goroutine 里**没有** recover，原因见第 02 章八股 3：命令执行到一半 panic，内存里的数据可能只改了一半，带着它继续服务比重启更危险。重启以后，从 AOF 重放就能得到一个一致的状态。

#### 常见追问

**追问：panic 时，已经加上的锁会被释放吗？**

如果解锁写在 defer 里，会。defer 在 panic 沿调用栈往上走的时候依次执行。这也是“加锁后立刻 defer 解锁”的另一个好处。但锁被释放了，不代表数据是一致的，这正是 Mini-Redis 不 recover 的原因。

### 八股 4：fsync 是什么？fsync 失败了能重试吗？

#### 一分钟口述版

> 调用 write 写文件，数据通常只写进了操作系统的页缓存，write 就返回了；操作系统过一段时间才会把它真正写到磁盘上。这时候机器断电，数据就丢了。fsync 是要求操作系统“现在就把这个文件的数据写到磁盘上，写完再返回”，它返回成功，数据才算持久化。它的代价是慢，要等磁盘，通常是毫秒级。一个容易被忽略的问题是：fsync 失败以后，不能简单地重试。在 Linux 上，fsync 报告写回失败以后，那些写失败的脏页可能已经被标记成干净的了，再调用一次 fsync 会返回成功，但数据其实已经丢了。2018 年 PostgreSQL 就是因为这个问题，改成了 fsync 一失败就让数据库停下来，从日志恢复。所以正确的做法是：fsync 失败就认为这次以及之后的写入都不可信，停止接受写入。

#### 要点

**一次写入经过的几层：**

```text
应用的缓冲区 ─write→ 操作系统页缓存 ─fsync→ 磁盘
```

- 只调用 write：进程崩溃不会丢（数据已经在内核里了），**机器**断电或内核崩溃会丢。
- 调用 fsync 并成功返回：机器断电也不会丢（前提是磁盘本身没有说谎，比如没有不带电池保护的写缓存）。
- 在 Go 里，`file.Sync()` 就是 fsync。Linux 上调用的是 fsync，Windows 上是 FlushFileBuffers。

**Redis 的两种持久化：**

| | AOF | RDB |
|---|---|---|
| 存什么 | 每一条写命令，追加到文件末尾 | 某一时刻的完整数据快照 |
| 恢复 | 从头重放所有命令，慢 | 直接加载快照，快 |
| 丢多少数据 | 取决于 fsync 策略：`always` 不丢、`everysec` 最多丢 1 秒、`no` 交给操作系统 | 丢掉上次快照之后的所有写入 |
| 文件大小 | 不断增长，要定期重写（AOF rewrite）压缩 | 紧凑 |

Redis 默认用 `everysec`，在性能和安全之间折中。Redis 4.0 起还支持混合持久化：AOF 重写时，文件开头是 RDB 格式的快照，后面跟着增量命令。

#### 项目里的例子

**Mini-Redis 只用 `always` 一种策略**：每条写命令都要 write + fsync 成功，才修改内存、回复客户端。所以“回复成功的写入，断电后不会丢”。代价是每条写命令都要等磁盘，写入的吞吐量受磁盘限制。

**写入失败以后的处理**，正好对应 fsync 不能重试的问题。`aof.Store.Append` 写入或 fsync 失败时，调用 `fail`：
1. 把文件截断回上一次确认成功的长度，去掉可能写了一半的记录；
2. 再 fsync 一次；
3. 把原始错误和截断、fsync 的错误用 `errors.Join` 合在一起，存进 `s.failed`；
4. **之后所有的 Append 都直接返回这个错误**，不再尝试写入。

引擎那边收到错误，就不修改内存，给客户端回复 `-ERR persistence write failed`。服务进入“只读”状态：读命令照常，写命令全部失败，需要人检查磁盘、重启。[aof/store_test.go](../../aof/store_test.go) 的 `TestWriteAndSyncFailuresAreSticky` 专门检查“失败一次以后一直拒写”。

**启动时遇到坏日志**，分两种情况：
- 文件末尾有半条命令：通常是上次写到一半时进程崩溃了。这条命令没有回复过客户端，丢掉是安全的。所以截断到最后一条完整的记录，fsync，继续启动。
- 中间有一条格式错误的完整记录：说明文件被损坏或者被改过，这种情况不能自动修，拒绝启动，交给人处理。

**收尾时用 errors.Join 合并错误。** `aof.Open` 中途失败时，要关闭已经打开的文件，而关闭本身也可能出错。代码在 defer 里写 `err = errors.Join(err, file.Close())`，两个错误都不会丢（代码走读 3）。

#### 常见追问

**追问 1：每条写都 fsync，太慢了，怎样提高吞吐量？**

常见的办法是**组提交**：把同一时间到达的多条写命令攒在一起，一次 write、一次 fsync，再一起回复。延迟不变，吞吐量成倍提高。数据库的 WAL 普遍这样做。Mini-Redis 没有做，因为写路径持有 logMu，写入本来就是串行的；要做组提交，写路径的结构要改得复杂很多。

**追问 2：为什么持有分片锁的时候做 fsync？不能先放锁吗？**

如果先修改内存、放锁，再 fsync，那么 fsync 之前，别的客户端就已经能读到这个值了；万一 fsync 失败，客户端读到的就是一个没有持久化的值。Mini-Redis 选择了“先日志后内存，日志确认前不让任何人看到新值”，代价是同一分片上的读要等 fsync。第 02 章八股 1 的“调度器不会替你释放锁”说的就是这个代价。

## 关键设计与为什么

**1. 先日志，后内存。**
- 写命令先算出计划，日志落盘以后才执行 `apply`。日志写失败，内存里什么也没发生，客户端不会读到一个没有持久化的值。
- 实现上靠 `writePlan` 把“回复什么、记什么、怎么改”放在一起，日志确认之前不碰内存。

**2. 日志记的是“效果”，不是原样的命令。**
- `EXPIRE a 100` 记成 `__EXPIREATMS a <到期时刻的毫秒数>`。如果记原命令，重启时会从重启那一刻重新算 100 秒，key 就多活了一段时间。`EXPIRE` 一个非正数等于删除，记成 `DEL`。
- 新建的列表记成 `_LNEW`。惰性删除不写日志：一个过期的列表被访问时悄悄删掉了，日志里看不出来。如果这时的 LPUSH 还记成 LPUSH，重放时旧列表还在（它在日志里从没被删过），新元素就会接到旧元素后面。`_LNEW` 告诉重放：“不管原来有什么，从一个空列表开始”。它和 LPUSH 一样长、参数个数一样，最大的合法请求记进日志也不会超出协议上限。
- 没有效果的写（DEL 不存在的 key）不记。
- 两个私有命令名以下划线开头，客户端直接发会得到 unknown command，只有重放能用。

**3. 只截断“读到一半就到了文件末尾”的记录。**
- 半条记录：上次写到一半时进程崩溃了，这条命令从没回复过 OK，丢掉是安全的。
- 一条完整却格式不对的记录：可能是磁盘坏了、文件被人改了。如果也截断，就会悄悄丢掉后面所有已经确认过的数据，所以拒绝启动，报出位置，交给人处理。

**4. 写失败一次，之后一直拒写。**
- fsync 失败后重试可能“成功”，但数据其实已经丢了。与其冒这个险，不如停止接受写入，等人处理。

**5. 文件独占锁，并且先占端口再恢复。**
- 两个进程同时写一个 AOF，记录会交错，文件就坏了。启动时先拿文件锁，拿不到就退出。
- `cmd/server` 先 `net.Listen` 再 `aof.Open`：不小心启动了第二个实例，它会在占端口这一步就失败，根本碰不到 AOF 文件。
- 锁由操作系统管理，进程崩溃时自动释放，不会留下需要手工删除的“锁文件”。

**6. 打开文件时不用追加模式（O_APPEND）。**
- Windows 上用追加模式打开的文件不能截断，而恢复和写失败时都要截断。所以用普通的读写模式打开，恢复完 Seek 到文件末尾，之后顺序写。单写者由文件锁和 `Store.mu` 保证。

## 动手实验

在一个空目录里做（服务端会在当前目录下建 `data/`），终端 1 启动服务端，终端 2 用客户端。下面的输出都是 2026-11-10 在 Windows 上实际运行的。

**实验 1：末尾有半条记录，启动时截断。**

先按“跑起来看什么”写入几条数据，停掉服务端。然后往文件末尾追加半条 SET（Git Bash）：

```text
printf '*3\r\n$3\r\nSET\r\n$1\r\nb' >> data/appendonly.aof
```

文件从 140 字节变成 158 字节。再启动服务端：

```text
Mini-Redis 服务端启动中....
2026/11/10 19:01:15 AOF recovery removed 18 incomplete tail bytes
开始监听....
```

`GET b` 是 `(nil)`，`GET a` 还是 `"2"`，文件回到 140 字节。

**实验 2：一条完整的记录坏了，拒绝启动。**

把文件里第一条记录的值 `$1\r\n1\r\n` 改成 `$1\r\n1X\n`（长度说是 1，后面却跟着 `1X\n`），再启动：

```text
Mini-Redis 服务端启动中....
2026/11/10 19:01:16 invalid AOF at byte 0: protocol error: bulk content missing CRLF
```

进程以退出码 1 结束。错误信息说明了在哪一步（`invalid AOF`）、文件的哪个位置（`byte 0`，第一条记录）、什么问题（内容后面不是 `\r\n`）。文件没有被修改。

**实验 3：两个进程抢同一个文件。**

一个服务端正在运行时，换一个端口、用同一个 AOF 文件再启动一个：

```text
go run ./cmd/server -addr :6380
```

```text
Mini-Redis 服务端启动中....
2026/11/10 19:01:17 lock AOF: The process cannot access the file because another process has locked a portion of the file.
```

第二个进程拿不到文件锁，直接退出。后面那句英文是 Windows 的系统错误，在 Linux 和 macOS 上会是 `resource temporarily unavailable`。

## 常见误区

- **用 `%v` 包装后，还想用 errors.Is 判断。** `%v` 只拼进了文字，链断了。
- **比较错误的字符串。** 字符串随时可能改，用 errors.Is 或 errors.As。
- **既打日志又返回错误。** 同一个错误在日志里出现好几次。
- **用 panic 处理普通错误。** 文件不存在、参数非法都应该返回 error。
- **defer 关闭文件，却忽略了 Close 的错误。** 对写入的文件，Close 和 Sync 的错误都可能意味着数据没写进去。
- **以为 write 返回成功，数据就安全了。** 还要 fsync。
- **fsync 失败后重试，成功了就当没事。** 数据可能已经丢了。

## 自测

**1. 开启 AOF 时，一条 SET 的磁盘写入失败了，客户端会看到什么？内存里的值变了吗？之后的写入呢？**

<details><summary>答案</summary>

客户端看到 `-ERR persistence write failed`。内存不变，因为 `apply` 只在 `Append` 成功后执行。`Store.fail` 把文件截断回上次确认的长度并记下错误，之后所有 `Append` 都直接返回这个错误，写命令全部失败，读命令照常。

</details>

**2. `Open` 里为什么一处用 `readErr == io.EOF`，另一处用 `errors.Is(readErr, io.EOF)`？**

<details><summary>答案</summary>

`ReadRequest` 只在一个字节都没读到时原样返回 `io.EOF`，表示文件刚好读完；读到半条记录就结束时，返回的是包装过的 EOF。`==` 只匹配原样的 `io.EOF`，用来判断“正常结束”；`errors.Is` 会沿着包装链找，用来判断“末尾有半条记录”。

</details>

**3. 为什么半条记录可以截断，一条格式错误的完整记录却要拒绝启动？**

<details><summary>答案</summary>

半条记录是写到一半时崩溃留下的，这条命令从没回复过客户端，丢掉是安全的。格式错误的完整记录说明文件损坏或被改过，它后面可能还有已经确认过的写入；如果截断，这些数据就悄悄丢了。

</details>

**4. 为什么 `EXPIRE a 100` 在日志里记成 `__EXPIREATMS` 加一个时间戳？**

<details><summary>答案</summary>

日志要记“效果”。如果记 `EXPIRE a 100`，重启时会从重启那一刻重新算 100 秒，key 多活了一段时间。记绝对的到期时刻，重放出来的期限和运行时完全一样。

</details>

**5. 客户端发来一条命令，引擎返回的错误里带着磁盘的路径，客户端会看到路径吗？**

<details><summary>答案</summary>

不会。路径只在 `commandError` 的 `cause` 里。`EncodeReply` 用 `errors.As` 找到 `RESPError` 方法，只取 code 和 message；找不到这个方法的错误，一律回复 `internal server error`。

</details>

**6. `lock_unix.go` 只在 Linux 和 macOS 上编译，是因为文件名吗？**

<details><summary>答案</summary>

不是。`unix` 不是一个操作系统名，文件名后缀对它不起作用。限定平台的是文件第一行的 `//go:build linux || darwin`。`lock_windows.go` 则是靠文件名后缀 `_windows`。

</details>
