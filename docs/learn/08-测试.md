## Go 基础

### 1. 测试文件和测试函数

- 测试写在 `xxx_test.go` 文件里，`go build` 会忽略它们，只有 `go test` 会编译。
- 测试函数的名字以 `Test` 开头，参数是 `*testing.T`。
- 测试文件的包名可以和被测代码一样（能访问未导出的名字，叫**白盒测试**）；也可以加上 `_test` 后缀，比如 `package kv_test`（只能用导出的 API，叫**黑盒测试**）。
- `testdata/` 目录会被 go 命令忽略，专门放测试用的数据文件。

下面是本章用的示例包，它把一行文本命令拆成命令名和参数：

```go
// 文件 kv.go
package kv

import "strings"

// ParseCommand 把 "set k v" 这样的一行拆成命令名和参数，命令名统一成大写。
func ParseCommand(line string) (string, []string) {
	fields := strings.Fields(line)
	if len(fields) == 0 {
		return "", nil
	}
	return strings.ToUpper(fields[0]), fields[1:]
}
```

### 2. 表格驱动测试和子测试

把输入和期望输出写成一张表，循环执行。加一个用例只需要加一行：

```go
// 文件 kv_test.go
package kv

import (
	"slices"
	"strings"
	"testing"
)

func TestParseCommand(t *testing.T) {
	tests := []struct {
		name     string
		line     string
		wantCmd  string
		wantArgs []string
	}{
		{"小写命令名", "set k v", "SET", []string{"k", "v"}},
		{"多余空白", "  GET   k  ", "GET", []string{"k"}},
		{"没有参数", "PING", "PING", []string{}},
		{"空行", "", "", nil},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) { // 每个用例是一个子测试，可以单独运行
			cmd, args := ParseCommand(tt.line)
			if cmd != tt.wantCmd || !slices.Equal(args, tt.wantArgs) {
				t.Errorf("ParseCommand(%q) = %q, %q；想要 %q, %q", tt.line, cmd, args, tt.wantCmd, tt.wantArgs)
			}
		})
	}
}
```

运行 `go test -v -run TestParseCommand`：

```text
=== RUN   TestParseCommand
=== RUN   TestParseCommand/小写命令名
=== RUN   TestParseCommand/多余空白
=== RUN   TestParseCommand/没有参数
=== RUN   TestParseCommand/空行
--- PASS: TestParseCommand (0.00s)
    --- PASS: TestParseCommand/小写命令名 (0.00s)
    --- PASS: TestParseCommand/多余空白 (0.00s)
    --- PASS: TestParseCommand/没有参数 (0.00s)
    --- PASS: TestParseCommand/空行 (0.00s)
PASS
```

只运行其中一个子测试：`go test -run 'TestParseCommand/多余空白'`。

### 3. testing.T 的常用方法

| 方法 | 作用 |
|---|---|
| `t.Errorf` | 记录失败，**继续**执行这个测试 |
| `t.Fatalf` | 记录失败，**立刻结束**这个测试。只能在测试自己的 goroutine 里调用，在别的 goroutine 里调用不会结束测试 |
| `t.Helper()` | 写在辅助函数开头。失败时报告的行号是调用辅助函数的那一行，而不是辅助函数内部 |
| `t.Cleanup(f)` | 注册一个收尾函数，测试结束时执行（后注册的先执行）。比 defer 好的地方是：辅助函数可以替调用者注册收尾 |
| `t.TempDir()` | 创建一个临时目录，测试结束时自动删除 |
| `t.Parallel()` | 和其他调用了 Parallel 的测试并行运行 |
| `t.Context()` | Go 1.24 起：一个在测试结束前被取消的 context |
| `t.Setenv(k, v)` | 设置环境变量，测试结束时恢复 |

### 4. 常用的 go test 参数

| 参数 | 作用 |
|---|---|
| `-run 正则` | 只运行名字匹配的测试；`-run '^$'` 表示一个都不运行，配合 `-bench` 或 `-fuzz` 用 |
| `-v` | 打印每个测试的名字和结果 |
| `-count=1` | 不使用缓存的结果，一定重新运行 |
| `-race` | 打开竞态检测（八股 1） |
| `-bench 正则` / `-benchmem` | 运行基准测试；同时报告内存分配（八股 2） |
| `-fuzz 名字` / `-fuzztime 10s` | 运行模糊测试（八股 4） |
| `-cover` / `-coverprofile=c.out` | 测试覆盖率；再用 `go tool cover -html=c.out` 在浏览器里看哪些行没有被覆盖 |
| `-cpuprofile` / `-memprofile` | 生成 pprof 文件（八股 3） |
| `-timeout 180s` | 超时就失败，并打印所有 goroutine 的堆栈，排查卡死很有用 |
| `-list 正则` | 只列出测试的名字，不运行 |

**`go test` 会自动跑一部分 `go vet` 检查**，但只是一个子集。复制锁（copylocks）、忘记调用 cancel（lostcancel）、WaitGroup 用错（waitgroup）这几项都**不在**里面，要单独运行 `go vet ./...`。

## 代码走读：项目里的几种测试写法

### 1. 表格驱动：一张表列出所有边界

[database/engine_test.go](../../database/engine_test.go) 的 `TestListRangeBoundaries` 固定一个三元素的列表，用一张表列出 LRANGE 的各种下标：包含两端、负下标、越界裁剪、start 大于 stop、int64 的极值。加一个边界，只要在表里加一行。

### 2. 替身：把难控制的东西换掉

| 替身 | 在哪里 | 换掉了什么 | 为什么 |
|---|---|---|---|
| `clockEngine` | [database/ttl_test.go](../../database/ttl_test.go) | 引擎的时钟 `e.now` | “5 秒后过期”不用真等 5 秒；时钟用 `atomic.Int64` 存，并发测试里拨动时钟也不会有数据竞争 |
| 假日志 | [database/persistence_test.go](../../database/persistence_test.go)、[golden_test.go](../../database/golden_test.go) | `CommandLog` | 一个每次都失败，用来检查“日志失败时内存不变”；一个只记录参数，用来固定 AOF 记录的序列 |
| `delayedExecutor` | [server/shutdown_test.go](../../server/shutdown_test.go) | 引擎 | 让一条命令卡在执行中，测试决定什么时候放行，从而制造“执行中收到停机”的场景 |
| `engine.reclaim` | [database/cleanup_test.go](../../database/cleanup_test.go) | `debug.FreeOSMemory` | 在“归还内存”被调用的那一刻，用 `TryLock` 检查所有分片锁都没被持有 |

这些替身之所以能换进去，是因为生产代码本来就依赖接口（`CommandLog`、`Executor`）或函数字段（`now`、`reclaim`），而不是写死的具体实现（第 03 章）。

### 3. 不用 sleep 等结果

停机测试要的是“先 A 后 B”的确定顺序，靠 sleep 猜时间，机器一慢就会偶尔失败。项目里的做法：

- `delayedExecutor` 开始执行时关闭 `started` channel，测试 `<-executor.started` 等到它真的开始；
- `closeObservedListener` 包住监听器，监听器真的被关闭时关闭一个 channel，测试等到它，再放行执行器；
- 用 `net.Pipe` 代替真实的 TCP 连接：它是同步的，写入要等对方读走才返回，顺序完全确定。

### 4. golden：整段输出逐字节比较

[server/golden_test.go](../../server/golden_test.go) 用原始字节发出一整段请求，把收到的所有回复和 `testdata/session.golden` 比较，不一致就把两边都打印出来。它**没有**“自动更新 golden 文件”的开关：golden 一变，必须先弄清楚是行为变了还是测试错了。

### 5. 真的杀掉一个进程

[aof/store_test.go](../../aof/store_test.go) 的 `TestThousandWritesSurviveForcedProcessTermination` 想验证“确认过的写入，进程被强杀后不丢”。它用的办法是让测试程序启动**自己**：

- 用 `exec.Command(os.Args[0], "-test.run=^TestCrashProcessHelper$")` 再运行一次测试二进制，只跑助手测试 `TestCrashProcessHelper`，并用环境变量告诉它“你是子进程”；
- 子进程写 1000 条 SET，每条都等确认，然后打印 `READY`；
- 父进程读到 `READY`，直接 `Kill` 子进程，不给它任何正常关闭、额外刷盘的机会；
- 父进程用同一个 AOF 文件重新打开引擎，检查 1000 个 key 全都在，而且文件锁已经被操作系统释放。

注释里写明了它的边界：这验证的是**进程崩溃**，不是机器断电。

## Go 八股

### 八股 1：`-race` 的原理是什么？它能发现什么，不能发现什么？

#### 一分钟口述版

> 数据竞争是指两个 goroutine 同时访问同一块内存，至少有一个是写，而且它们之间没有同步，比如没有用同一把锁，也没有通过 channel 传递。`-race` 打开 Go 的竞态检测器，它基于 C++ 的 ThreadSanitizer。编译时，编译器在每一次内存读写前面插入检测代码；运行时，检测器为每个 goroutine 维护一个向量时钟，加锁解锁、channel 收发这些同步操作会更新时钟，用来判断两次访问之间有没有“先行发生”的关系。没有的话，就报告一次数据竞争，并打印两次访问各自的堆栈。它的局限是：只能发现**这次运行中实际发生了**的竞争，没有执行到的代码、这次没有碰上的交错顺序，它都发现不了，所以测试要尽量让并发的路径真的跑起来；它的开销也很大，内存多用 5 到 10 倍，速度慢 2 到 20 倍，一般只在测试和 CI 里打开。它报出来的问题基本都是真问题，没有误报。

#### 要点

同一个测试，不加 `-race` 时通过，加上就失败：

```go
package race

import (
	"sync"
	"testing"
)

func TestCounter(t *testing.T) {
	count := 0
	var wg sync.WaitGroup
	for range 2 {
		wg.Go(func() {
			count++ // 两个 goroutine 同时读写 count，没有加锁
		})
	}
	wg.Wait()
	if count != 2 {
		t.Log("这次结果是", count)
	}
}
```

```text
> go test .
ok  	race	0.338s

> go test -race .
==================
WARNING: DATA RACE
Read at 0x00c00010e238 by goroutine 10:
  race.TestCounter.func1()
      .../counter_test.go:13 +0x2e

Previous write at 0x00c00010e238 by goroutine 9:
  race.TestCounter.func1()
      .../counter_test.go:13 +0x44
...
==================
--- FAIL: TestCounter (0.00s)
    testing.go:1865: race detected during execution of test
FAIL
```

不加 `-race` 时，`count` 恰好等于 2，测试就通过了。这正是数据竞争危险的地方：它大部分时候不出错，偶尔出错，而且很难复现。

| `-race` 能做到 | 做不到 |
|---|---|
| 发现这次运行中实际发生的竞争 | 发现没执行到的代码里的竞争 |
| 给出两次访问的位置和 goroutine 的创建位置 | 发现死锁（那是另一类问题，见第 04 章） |
| 几乎没有误报 | 发现逻辑上的并发错误，比如两次加锁之间状态被改了（第 04 章 lockRead 的重新检查） |

在 Windows 上，`-race` 需要 cgo：`CGO_ENABLED=1`，并且能找到 gcc。

#### 项目里的例子

- [CI](../../.github/workflows/ci.yml) 的测试步骤就是 `go test -race ./... -count=1 -timeout=180s`，每次提交都会跑。
- 为了让 `-race` 有东西可查，项目专门写了并发测试：[database/engine_test.go](../../database/engine_test.go) 的 `TestConcurrentListAndMultiKeyCommands` 让 8 个 goroutine 同时 SET、EXISTS、反序 DEL 和 LPUSH 同一个列表；[database/ttl_test.go](../../database/ttl_test.go) 的 `TestConcurrentExpirationAndCleanup` 让命令和后台清理同时访问期限。如果分片锁哪里漏了，`-race` 会在这里报出来。

#### 常见追问

**追问：线上能开 `-race` 吗？**

一般不开，开销太大。有的团队会在灰度环境用一小部分流量跑带 `-race` 的版本，专门抓测试没覆盖到的竞争。

### 八股 2：benchmark 怎样写才可信？

#### 一分钟口述版

> 基准测试的函数以 Benchmark 开头，参数是 `*testing.B`。Go 1.24 起推荐写成 `for b.Loop() { ... }`：循环之前的准备工作自动不计时，循环里调用的结果会被保留，编译器不会因为“结果没人用”就把被测的代码优化掉。老的写法是 `for i := 0; i < b.N; i++`，要自己调用 ResetTimer 把准备工作排除，还要把结果存到一个全局变量里，防止被优化掉。要得到可信的结果，有几点要注意：加 `-benchmem` 同时看每次操作的内存分配；用 `-count=10` 多跑几次，再用 benchstat 比较两组结果，看差异是不是统计上显著；跑的时候机器要空闲，笔记本要插电；被测的代码要贴近真实的使用方式，比如并发的场景用 RunParallel。最后，benchmark 只说明在这个负载下的表现，不能随便外推到别的场景。

#### 要点

```go
func BenchmarkParseCommand(b *testing.B) {
	line := "SET user:1000 " + strings.Repeat("x", 64) // 准备工作，不计时
	for b.Loop() {
		ParseCommand(line)
	}
}
```

运行 `go test -run '^$' -bench . -benchmem`：

```text
cpu: AMD Ryzen 7 9700X 8-Core Processor
BenchmarkParseCommand-16    	16402002	        74.22 ns/op	      48 B/op	       1 allocs/op
```

| 字段 | 意思 |
|---|---|
| `-16` | GOMAXPROCS 是 16 |
| `16402002` | 一共执行了多少次 |
| `74.22 ns/op` | 平均每次 74.22 纳秒 |
| `48 B/op` | 每次分配 48 字节 |
| `1 allocs/op` | 每次分配 1 次。这次分配来自 `strings.Fields` 返回的切片：3 个字符串，每个 16 字节 |

**b.Loop 和 b.N 的区别：**

| | `for b.Loop()`（Go 1.24 起） | `for i := 0; i < b.N; i++` |
|---|---|---|
| 准备工作 | 第一次调用 Loop 时自动重置计时器 | 要手动 `b.ResetTimer()` |
| 被测代码被优化掉 | 循环里的调用结果会被保留 | 要手动把结果存进全局变量 |
| 基准函数执行几次 | 每次测量只执行一次 | 会以不同的 b.N 执行好几次，准备工作也跟着执行好几次 |

**让结果可信的清单：**
- `-benchmem`：分配次数往往比耗时更能说明问题。
- `-count=10` 加 `benchstat`（`golang.org/x/perf/cmd/benchstat`）：两组结果比较，给出差异和置信区间。
- 机器空闲；关掉省电模式；固定 GOMAXPROCS。
- 并发的场景用 `b.RunParallel`，让多个 goroutine 同时跑。
- 写清楚测试条件：CPU、Go 版本、数据规模、负载的读写比例。

#### 项目里的例子

- [database/benchmark_test.go](../../database/benchmark_test.go) 的 `BenchmarkEngine` 先写入 10000 个 key（64 字节的值），用两层子基准组合“负载 × 分片数”：负载有读多写少、纯写、热点三种，分片数有 1、16、64 三种；然后用 `b.RunParallel` 让 16 个 goroutine 同时读写。每个 worker 用自己的伪随机序列（xorshift）选 key，不共用一个带锁的随机数生成器，否则那把锁本身会成为被测的竞争。
- README 里的数字是每格跑三次取中位数，并写明了 CPU、Go 版本、GOMAXPROCS 和数据规模，还说明了这些数值只测引擎，不能外推到开启持久化或经过网络的情况。第 04 章的配角用这张表解释了分片的效果。
- 这个基准用的是 `b.ResetTimer` 加 `RunParallel` 的写法，RunParallel 自己管理循环次数。
- **一次真实的教训**：第 04 章的配角里，同一台机器、同样的代码，10 月测的热点负载是 390 纳秒左右，11 月再测是 600 纳秒左右。代码没变，变的是机器当时的状态。所以比较改造前后，用的是“两个版本在同一时段交替各跑 4 次”，结论是差异在噪声范围内；而不是拿 11 月的新数字去和 10 月的旧数字比。

#### 常见追问

**追问：两次跑的结果差了 5%，能说明优化有效吗？**

不能直接说明。机器的波动常常就有这么大。要多跑几次，用 benchstat 看差异的置信区间；它会标出“~”表示差异不显著。

### 八股 3：怎样用 pprof 排查性能问题？

#### 一分钟口述版

> pprof 是 Go 自带的性能分析工具。最常用的是 CPU profile：运行时每秒采样 100 次，记下当时正在执行的调用栈，统计下来就知道时间花在了哪些函数上。heap profile 看内存，分两种视角：inuse 是现在还占着的内存，用来查泄漏；alloc 是累计分配过的，用来查哪里分配太频繁、给 GC 造成压力。goroutine profile 列出所有 goroutine 卡在哪一行，查卡死和泄漏。block 和 mutex profile 看 goroutine 在 channel 和锁上等了多久，要先设置采样率才会记录。获取的方式有两种：测试和基准里加 `-cpuprofile`、`-memprofile`；运行中的服务引入 `net/http/pprof`，通过 HTTP 接口实时抓取。分析用 `go tool pprof`，`top` 看最耗时的函数，`list 函数名` 看具体到行，`-http` 打开网页版的火焰图。

#### 要点

**几种 profile：**

| profile | 看什么 | 用来查 |
|---|---|---|
| CPU | 每秒采样 100 次正在执行的调用栈 | 时间花在哪里 |
| heap（inuse） | 当前还活着的对象是在哪里分配的 | 内存泄漏 |
| allocs（alloc） | 累计的分配 | 分配太频繁、GC 压力大 |
| goroutine | 所有 goroutine 的调用栈 | 卡死、goroutine 泄漏 |
| goroutineleak（Go 1.27） | 判定为泄漏的 goroutine | goroutine 泄漏（第 07 章八股 3） |
| block | 在 channel、select、条件变量上等待的时间。需要 `runtime.SetBlockProfileRate` | 等待太久 |
| mutex | 锁竞争造成的等待。需要 `runtime.SetMutexProfileFraction` | 锁竞争 |

**获取：**

```text
# 测试和基准
go test -run '^$' -bench BenchmarkEngine -cpuprofile cpu.out -memprofile mem.out ./database

# 运行中的服务（代码里 import _ "net/http/pprof"，并启动一个只监听本机的 HTTP 服务）
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30
curl http://127.0.0.1:6060/debug/pprof/goroutine?debug=2
```

**分析：**

```text
go tool pprof cpu.out
(pprof) top          # 最耗时的函数
(pprof) list fnv32   # 具体到每一行
go tool pprof -http=:8080 cpu.out   # 网页版，含火焰图
```

读 top 的输出时，注意两列：`flat` 是函数自己花的时间，`cum` 是包括它调用的函数在内的总时间。flat 高，说明这个函数本身慢；cum 高 flat 低，说明慢在它调用的函数里。

**pprof 的端口不要对外暴露**：它能看到程序的内部状态，还能让程序做一次耗时的采样。

#### 项目里的例子

- [docs/performance.md](../performance.md) 保存了一次真实的 CPU profile：用热点负载、16 个分片采样 10 秒，`go tool pprof -top` 的结果显示锁和调度相关的函数是主要热点。文档也写明了局限：CPU profile 看不到“睡着等锁”的时间，要分析等待，还得另做 mutex 和 block profile。
- Mini-Redis 没有引入 `net/http/pprof`。要给它加上，只需要在 main 里 import，再起一个只监听 127.0.0.1 的 HTTP 服务。

#### 常见追问

**追问：CPU 使用率不高，但请求很慢，用哪个 profile？**

CPU profile 只能看到“在 CPU 上跑”的时间，看不到“在等”的时间。请求慢但 CPU 不高，多半是在等锁、等 channel、等 IO。先看 goroutine profile，找到大量 goroutine 停在哪里；再打开 block 和 mutex profile，看等待集中在哪把锁或者哪个 channel 上。Go 自带的 trace 工具（`go test -trace`，`go tool trace`）能看到每个 goroutine 在时间线上的状态，也适合查这一类问题。

### 八股 4：模糊测试是什么？

#### 一分钟口述版

> 单元测试的输入是人想出来的，人想不到的情况就测不到。模糊测试反过来：你给出几个种子输入，再写一个“对任何输入都应该成立”的性质，比如“不会 panic”“解析出的参数里没有空白”“编码后再解码等于原值”，然后由 go test 自动变异输入，持续地跑。它会记录哪些输入走到了新的代码路径，围绕这些输入继续变异，所以比纯随机的输入更容易找到边界情况。找到失败的输入，会把它保存到 `testdata/fuzz` 下面，以后每次普通的 `go test` 都会跑一遍这个输入，相当于自动加了一条回归测试。Go 1.18 起原生支持。它特别适合测解析器、编解码这类处理外部输入的代码。

#### 要点

```go
func FuzzParseCommand(f *testing.F) {
	f.Add("set k v") // 种子输入
	f.Add("")
	f.Fuzz(func(t *testing.T, line string) {
		cmd, args := ParseCommand(line)
		if cmd != strings.ToUpper(cmd) {
			t.Errorf("命令名没有转成大写：%q", cmd)
		}
		for _, a := range args {
			if a == "" || strings.ContainsAny(a, " \t\r\n") {
				t.Errorf("参数里不应有空白：%q", a)
			}
		}
	})
}
```

**它能找到表格测试漏掉的 bug。** 把 ParseCommand 改成一个有 bug 的版本：只按空格切分，跳过空串，但忘了制表符和换行也是空白。上面的表格测试照样全部通过，因为表里没有制表符的用例。模糊测试 1 秒就找到了：

```text
> go test -run '^$' -fuzz FuzzParseCommand -fuzztime 30s .
fuzz: elapsed: 0s, gathering baseline coverage: 2/2 completed, now fuzzing with 16 workers
fuzz: elapsed: 1s, execs: 8225 (7026/sec), new interesting: 33 (total: 35)
--- FAIL: FuzzParseCommand (1.17s)
    --- FAIL: FuzzParseCommand (0.00s)
        kv_test.go:48: 参数里不应有空白："000000000000000\t00"

    Failing input written to testdata\fuzz\FuzzParseCommand\e736cedbe8bde6d7
    To re-run:
    go test -run=FuzzParseCommand/e736cedbe8bde6d7
FAIL
```

- `new interesting`：走到了新代码路径的输入个数，模糊测试会围绕它们继续变异。
- 失败的输入被保存下来。之后不加 `-fuzz` 的普通 `go test` 也会跑它，修好 bug 之前测试会一直失败。

**写好模糊测试的关键是想清楚“性质”**：对任何输入都应该成立的事情。常见的几种：
- 不 panic、不卡死；
- 往返一致：编码再解码，等于原值；
- 和一个简单但慢的参考实现结果相同；
- 输出满足某个约束，比如长度不超过上限。

#### 项目里的例子

- [resp/fuzz_test.go](../../resp/fuzz_test.go) 的 `FuzzReadRequest` 给了 13 个种子：空输入、正常的请求、两条连在一起的请求、负数长度、超过上限的数组长度和 bulk 长度、只有一半的请求、非法字符、超长的头部、只有 `\n` 没有 `\r` 的头部、空数组。性质是：
  - 要么返回参数、要么返回错误，二者必居其一；
  - 出错时报告的字节数是 0，不把残缺的输入当成完整的请求；
  - 成功时报告的字节数不超过输入的长度。
- 可读性改造的每一步都跑 10 秒的模糊测试冒烟：`go test ./resp -run '^$' -fuzz FuzzReadRequest -fuzztime 10s`。

#### 常见追问

**追问：模糊测试要在 CI 里一直跑吗？**

通常不会，太耗时间。CI 里普通的 `go test` 会跑种子和 `testdata/fuzz` 里保存的输入；长时间的模糊测试放在专门的机器上，或者像 Mini-Redis 一样，每次改动时跑一小段时间做冒烟。

### 配角：重构时，怎样证明行为没有变？

#### 一分钟口述版

> 重构的定义就是“改结构，不改行为”，所以第一件事是把“行为”固定下来。我在 Mini-Redis 的可读性改造里用的是 golden 测试：改代码之前，先写测试把系统对外的输出完整地录下来，存成文件，包括一整段 TCP 会话的所有回复字节、写命令产生的 AOF 记录、用一份旧的 AOF 文件恢复出来的状态。之后每一步重构，这三份文件都必须逐字节不变。但测试通过不一定说明测试有用，它可能什么都没检查到。所以我又做了变异测试：故意往代码里放几个 bug，比如去掉一条日志记录、重放时忽略过期时间、空请求也回复，确认每一个都会让某个 golden 测试失败。这比看覆盖率更能说明测试真的有效。

#### 要点

**golden 测试**：把一段输出完整地存成文件（golden 文件），测试时把实际输出和它逐字节比较。
- 好处：不用一条条写断言，就能把大量细节一次锁住，包括那些你没想到要检查的细节。
- 要求：输出必须是确定的。和时间有关的部分，要用固定的时钟，或者只录稳定的结果。
- 风险：如果测试里提供了“自动更新 golden”的开关，有人可能为了让测试通过而直接更新它。Mini-Redis 的 golden 测试**故意不提供**更新开关，可读性改造时定下的规矩是：golden 一变就停下来查原因，不能改 golden 让测试通过。

**变异测试**：故意改坏代码（变异），看测试能不能发现。发现不了，说明测试有漏洞。

**覆盖率的局限**：覆盖率只说明“这行代码执行过”，不说明“执行结果被检查过”。一个什么都不断言的测试，也能让覆盖率达到 100%。

#### 项目里的例子

可读性改造（PR #5）的第 1 步，在改任何生产代码之前，先加了三份 golden：

| golden | 锁住什么 |
|---|---|
| [server/testdata/session.golden](../../server/testdata/session.golden)（改造前在 tcp 包，随包迁移） | 一整段 TCP 会话的 53 条回复，共 773 字节：PING、SET/GET（值里含 `\r\n` 和 `\x00`）、列表操作、过期、各种错误、空数组不回复、协议错误后断开连接 |
| [database/testdata/aof-records.golden](../../database/testdata/aof-records.golden) | 一组写命令产生的 21 条 AOF 记录，包括新建列表记成 `_LNEW`、EXPIRE 记成绝对毫秒时间、没有效果的写不产生记录 |
| [database/testdata/legacy.aof](../../database/testdata/legacy.aof) 和 `legacy-state.golden` | 用一份手工构造的旧格式 AOF 恢复出来的状态，证明改造后还能读旧文件 |

复核这一步时做了三次变异：去掉 `_LNEW` 记录、重放时忽略 `__EXPIREATMS`、空数组也回复。三份 golden 各自抓住了其中一个。之后每一步改造，这三份文件都逐字节不变；session.golden 随 tcp 包改名移到了 server 包，Git 记录的是 100% 相同的重命名。

**改造做完以后，又做了一轮变异测试。** 这一次针对最容易出错的地方改坏了 14 处：停机的各个环节、AOF 截断、字节拷贝、客户端读回复、请求预算、加锁顺序、写失败后的拒写……10 处被测试抓住，4 处没有：

- 两道停机检查，单删任何一道，测试都不报错：现有测试里两道检查互相兜底（第 07 章动手实验 1）。
- `Shutdown` 给执行中的连接设写截止时间，删掉也不报错：这段代码本来就是多余的，超时的时候 `Shutdown` 会直接关闭所有连接。
- LPOP 弹空列表后不清期限，不报错：测试只检查了 TTL 返回 -2，而这个结果在没清期限时也成立。

处理办法是：给两道检查和 LPOP 各补一个能抓住它们的测试，删掉多余的那段代码。补完再变异一次，全部被抓住。这个过程说明：覆盖率很高（server 包 91.6%）的代码，照样可能有测试抓不住的改动。

另外两个细节：
- testdata 在 `.gitattributes` 里设成 `-text`，防止 Git 在 Windows 上把 `\n` 转成 `\r\n`，改变 golden 的字节。
- 测试的数量和名字在改造前后列表对照（`go test -list . ./...`），删掉的测试要说明它保护的行为现在由哪个测试保护。

## 关键设计与为什么

**1. 改结构之前，先把行为录下来。**
- 可读性改造的第一个提交只加测试、不改一行生产代码：三份 golden 加上 `go test -list` 的清单。之后每一步都拿它们对照。

**2. golden 文件不提供“自动更新”的开关。**
- 有了开关，测试失败时最省事的做法就是更新 golden，测试就失去了意义。没有开关，golden 一变就得停下来查原因。

**3. 用替身控制时间和顺序，不用 sleep。**
- 可控的时钟、会卡住的执行器、能观察到“关闭”的监听器、同步的 `net.Pipe`，让测试每次都按同样的顺序执行，不会因为机器忙而偶尔失败。

**4. 包内测试和包外测试各有用处。**
- 大多数测试和代码在同一个包里（`package database`），可以直接检查 `shards`、`expires` 这些内部状态，比如“LPOP 弹空以后，期限索引里也不能有残留”。
- 只测对外行为的测试（golden、TCP 会话），不依赖任何内部名字，内部重构时它们不用动。

**5. 测试本身也要被检验。**
- 覆盖率只能说明代码被执行过。故意改坏一处，看有没有测试失败，才能说明测试真的在检查。

## 动手实验

**实验 1：去掉“空数组不回复”，看 golden 怎样报错。**

在 [server/connection.go](../../server/connection.go) 的 `handle` 里，删掉这三行：

```go
if readErr == nil && len(args) == 0 {
	continue
}
```

运行 `go test ./server -count=1`，`TestSessionGolden` 失败，并打印出完整的实际回复和期望回复（这里只截取结尾）：

```text
--- FAIL: TestSessionGolden (0.00s)
    golden_test.go:94: TCP replies changed
         got: "...+PONG\r\n$6\r\na\r\nb\x00c\r\n-ERR unknown command\r\n$11\r\nafter-empty\r\n-ERR Protocol error\r\n"
        want: "...+PONG\r\n$6\r\na\r\nb\x00c\r\n$11\r\nafter-empty\r\n-ERR Protocol error\r\n"
```

实际回复多了一行 `-ERR unknown command`：空数组 `*0\r\n` 被当成一条没有命令名的请求交给了引擎。Redis 对空数组不回复，golden 里锁住了这个细节，所以一改就被发现。做完把三行改回来。

**实验 2：自己做一次变异测试。**

挑一处你读懂了的代码，想一想“改成什么样会出 bug”，改完跑 `go test ./...`，看有没有测试失败。几个可以试的地方：

| 改坏什么 | 在哪里 | 应该被哪个测试抓住 |
|---|---|---|
| `lockKeys` 不排序 | database/shard.go | `TestConcurrentListAndMultiKeyCommands` 卡死到超时（第 04 章实验 1） |
| `planWrite` 不拷贝值 | database/write.go | `TestEngineOwnsStoredAndReturnedBytes`（第 01 章实验 2） |
| 写完回复后不检查停机 | server/connection.go | `TestShutdownDrainsSingleInFlightReply`（第 07 章实验 1） |
| `Open` 把完整的坏记录也当成半条截断 | aof/store.go | `TestRejectCorruptOrInvalidCompleteRecordsWithoutTruncating` |
| Append 失败后不再拒写 | aof/store.go 的 `if s.failed != nil` | `TestWriteAndSyncFailuresAreSticky` |
| 客户端读数组时不读元素 | cmd/client/reply.go | `TestReadReplyArrayThenNextReply` 等 |

如果你改了一处，所有测试都还通过，那就找到了一个测试的漏洞：想想该补一个什么样的测试。

**实验 3：跑 10 秒模糊测试。**

```text
go test ./resp -run '^$' -fuzz FuzzReadRequest -fuzztime 10s
```

输出的最后几行（2026-11-10 实测）：

```text
fuzz: elapsed: 9s, execs: 6245218 (640474/sec), new interesting: 1 (total: 33)
fuzz: elapsed: 11s, execs: 6784687 (268424/sec), new interesting: 1 (total: 33)
PASS
```

10 秒左右，解析器被喂了将近 680 万个变异出来的输入，没有一个违反性质。`total: 33` 是目前收集到的“有意思的输入”个数，包括 13 个种子。

## 常见误区

- **只看测试通过，不看测试有没有检查东西。** 用变异测试验证测试本身。
- **不加 `-race` 跑并发测试。** 数据竞争大部分时候不出错，不加检测器就发现不了。
- **在别的 goroutine 里调用 `t.Fatal`。** 它不会结束测试。在别的 goroutine 里用 `t.Error`，或者把错误传回测试的 goroutine。
- **以为 `go test` 已经跑了全部 vet 检查。** 复制锁、lostcancel、waitgroup 这几项要单独跑 `go vet`。
- **benchmark 只跑一次就下结论。** 多跑几次，用 benchstat 比较。
- **用 sleep 等异步结果。** 机器一慢测试就不稳定。用 channel、WaitGroup 明确地等；要测和时间有关的并发代码，可以用 Go 1.25 正式加入的 `testing/synctest`，它在一个隔离的“气泡”里用假时间运行。
- **为了让测试通过，直接更新 golden 文件。** golden 变了，先弄清楚是行为变了还是测试本身有问题。
- **拿今天的 benchmark 数字和上个月文档里的数字比。** 机器状态变了，结论就不可信。要在同一时段交替运行两个版本。

## 自测

**1. 覆盖率 91.6% 的 server 包，为什么还有测试抓不住的改动？**

<details><summary>答案</summary>

覆盖率只说明代码被执行过。两道停机检查都被执行了，但现有测试里它们互相兜底：单删一道，另一道照样让连接退出，测试结果不变。要发现这种漏洞，得故意改坏代码，看测试会不会失败。

</details>

**2. `clockEngine` 解决了什么问题？为什么时钟要用 `atomic.Int64` 存？**

<details><summary>答案</summary>

它让测试可以手动拨动引擎的时钟，“5 秒后过期”不用真的等 5 秒，结果也不受机器快慢影响。有的测试一边并发执行命令、一边拨动时钟，用原子变量存时间，`-race` 才不会报数据竞争。

</details>

**3. 怎样测试“进程被强杀以后，确认过的写入不丢”？**

<details><summary>答案</summary>

让测试二进制再启动自己，只运行一个助手测试作为子进程：子进程写 1000 条并确认，打印 READY；父进程读到后直接 Kill 子进程，再用同一个 AOF 文件打开引擎，检查数据都在、文件锁已经释放。

</details>

**4. golden 测试为什么不提供“自动更新 golden 文件”的开关？**

<details><summary>答案</summary>

有了开关，测试失败时最省事的做法就是重新生成 golden，测试就失去了保护作用。没有开关，golden 一变就必须停下来，弄清楚是行为真的变了，还是测试有问题。

</details>

**5. 改造前后各跑一次 benchmark，改造后慢了 30%，能说明改造让代码变慢了吗？**

<details><summary>答案</summary>

不能。如果两次是在不同的时间跑的，机器状态可能完全不同。要在同一时段交替运行两个版本，多跑几次，看差异是不是稳定、是不是超出了同一版本自身的波动。Mini-Redis 就是这样做的，结论是差异在噪声范围内。

</details>

**6. 模糊测试 `FuzzReadRequest` 检查的“性质”是什么？**

<details><summary>答案</summary>

对任何输入：要么返回参数、要么返回错误，二者必居其一；出错时报告的字节数是 0；成功时报告的字节数不超过输入的长度。当然还有最基本的一条：不 panic。

</details>
