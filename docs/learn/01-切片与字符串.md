# 第 01 章：切片与字符串

本章在项目里对应 **resp 包**：从 TCP 字节流里读出一条完整的命令，再把执行结果编码成字节写回去。这两件事做的全是切片和字节的操作。

## 跑起来看什么

第 00 章用客户端发命令，看到的是 `OK`、`"redis"` 这样整理过的结果。这一章直接看线上传的字节。

先启动服务端（`go run ./cmd/server -aof=`），再运行下面的小程序（放在仓库里的临时目录，例如 `tmpexp/raw/main.go`，用 `go run ./tmpexp/raw` 运行）。它绕过客户端，直接往 TCP 连接上写原始字节，读回原始字节：

```go
package main

import (
	"fmt"
	"net"
	"time"
)

func main() {
	conn, err := net.Dial("tcp", "127.0.0.1:6379")
	if err != nil {
		panic(err)
	}
	defer conn.Close()
	read := func() {
		_ = conn.SetReadDeadline(time.Now().Add(300 * time.Millisecond))
		buf := make([]byte, 1024)
		n, err := conn.Read(buf)
		if n == 0 {
			fmt.Println("没收到数据:", err)
			return
		}
		fmt.Printf("收到 %q\n", buf[:n])
	}

	// 1. 一次写入两条请求（流水线），值里含 \r\n 和 \x00
	conn.Write([]byte("*3\r\n$3\r\nSET\r\n$1\r\nk\r\n$5\r\na\r\nb\x00\r\n*2\r\n$3\r\nGET\r\n$1\r\nk\r\n"))
	time.Sleep(100 * time.Millisecond)
	read()

	// 2. 一条请求分两次到达（半包）
	conn.Write([]byte("*2\r\n$3\r\nGE"))
	read()
	conn.Write([]byte("T\r\n$7\r\nmissing\r\n"))
	read()

	// 3. 不是数组开头的请求
	conn.Write([]byte("PING\r\n"))
	read()
	read()
}
```

输出：

```text
收到 "+OK\r\n$5\r\na\r\nb\x00\r\n"
没收到数据: read tcp 127.0.0.1:53559->127.0.0.1:6379: i/o timeout
收到 "$-1\r\n"
收到 "-ERR Protocol error\r\n"
没收到数据: EOF
```

逐条看：

1. 两条请求一次写过去，这次一次 Read 就读到了两条回复：`+OK\r\n` 是 SET 的回复，`$5\r\na\r\nb\x00\r\n` 是 GET 的回复。值 `a\r\nb\x00` 里有换行也有零字节，因为前面先写了长度 5，按长度读，所以不会读错。不过，一次 Read 能读到多少字节是不确定的，这正是本章要讲的“粘包和半包”。如果你这里只读到了 `+OK\r\n`，剩下的字节会留到下一次 Read，后面几行的输出就会错开，再跑一次就行。
2. 只发了半条请求，服务端一直等，300 毫秒内没有回复；补上后半条，才收到 `$-1\r\n`（key 不存在）。
3. `PING\r\n` 不是 RESP 数组，服务端回一行协议错误，然后关闭连接，所以再读就是 EOF。

这一章要弄懂的，就是服务端怎样从一串字节里切出一条一条的请求。

## Go 基础

### 1. 数组和切片

**数组**的长度是类型的一部分：`[3]int` 和 `[4]int` 是两种不同的类型。数组是值类型，赋值和传参都会拷贝全部元素。所以实际写代码时很少直接用数组，大多用切片。

**切片**是对一段数组的“视图”。它本身只有三个字段：指向底层数组的指针、长度 `len`、容量 `cap`。

```go
package main

import "fmt"

func main() {
	arr := [5]int{10, 20, 30, 40, 50}
	s := arr[1:3] // 从下标 1 到 3，不含 3
	fmt.Println(s, len(s), cap(s))

	s[0] = 99 // 修改切片，就是修改底层数组
	fmt.Println(arr)

	t := make([]int, 2, 10) // 长度 2，容量 10
	fmt.Println(t, len(t), cap(t))

	var n []int // nil 切片：可以直接 append、range、取 len
	n = append(n, 1)
	fmt.Println(n)
}

// 输出：
// [20 30] 2 4
// [10 99 30 40 50]
// [0 0] 2 10
// [1]
```

- `len`：切片里现在有几个元素，下标不能超过它。
- `cap`：从切片的起点到底层数组的末尾，一共还有多少位置。上面 `s` 从 `arr[1]` 开始，后面还有 4 个位置，所以容量是 4。
- 切片表达式 `a[low:high]` 不会拷贝数据，新切片和原来的共享同一个底层数组。

### 2. append 和 copy

- `append(s, x...)`：容量够，就直接写进底层数组；容量不够，就分配一个更大的新数组，把旧数据拷过去，再写入。**所以必须用返回值接住：`s = append(s, x)`。**
- `copy(dst, src)`：拷贝 `min(len(dst), len(src))` 个元素，返回拷贝了几个。需要一份独立的副本时用它，或者用 `slices.Clone`、`bytes.Clone`（Go 1.20 起）。

```go
package main

import (
	"bytes"
	"fmt"
)

func main() {
	src := []byte("hello")

	dst := make([]byte, len(src))
	n := copy(dst, src)
	dst[0] = 'H'
	fmt.Println(n, string(src), string(dst))

	c := bytes.Clone(src) // 同样得到一份独立的副本
	c[0] = 'J'
	fmt.Println(string(src), string(c))
}

// 输出：
// 5 hello Hello
// hello Jello
```

### 3. 字符串、byte 和 rune

- `string` 是**只读**的字节序列。`len(s)` 是字节数，不是字符数。
- `s[i]` 取到的是第 i 个**字节**（`byte`）。
- `for i, r := range s` 按 **UTF-8 字符**遍历，`r` 是 `rune`，`i` 是这个字符第一个字节的下标。
- 反引号写的是原样字符串，里面的 `\n` 不会被转义，适合写正则或多行文本。

```go
package main

import (
	"fmt"
	"unicode/utf8"
)

func main() {
	s := "Go语言"
	fmt.Println(len(s), utf8.RuneCountInString(s)) // 一个汉字在 UTF-8 里占 3 个字节

	for i, r := range s {
		fmt.Print(i, ":", string(r), " ")
	}
	fmt.Println()

	fmt.Println(s[0], s[2]) // 按字节取：'G' 是 71，s[2] 是“语”的第一个字节
}

// 输出：
// 8 4
// 0:G 1:o 2:语 5:言
// 71 232
```

### 4. 拼接字符串

字符串不可变，所以 `s += x` 每次都会分配一个新字符串，把旧内容和新内容拷进去。在循环里这样拼，总拷贝量是平方级的。拼很多段时用 `strings.Builder`：它内部维护一个 `[]byte`，用 append 的方式往后写，最后一次性转成 string。

```go
package main

import (
	"fmt"
	"strconv"
	"strings"
)

func main() {
	var b strings.Builder
	for i := 0; i < 3; i++ {
		b.WriteString("item")
		b.WriteString(strconv.Itoa(i))
		b.WriteByte(' ')
	}
	fmt.Println(b.String())

	// 拼的是字节而不是字符串时，直接往 []byte 上 append，strconv.AppendInt 也是这样用的
	buf := []byte("len=")
	buf = strconv.AppendInt(buf, 42, 10)
	buf = append(buf, '\r', '\n')
	fmt.Printf("%q\n", buf)
}

// 输出：
// item0 item1 item2
// "len=42\r\n"
```

### 5. io.Reader 和 bufio

`io.Reader` 是 Go 里“能读出字节的东西”的统一接口，网络连接、文件、内存里的字符串都实现了它：

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

它的约定有两点容易忽略：
- **一次 Read 可能只读到一部分**，n 可以小于 `len(p)`。从网络上读时，这是常态。
- 读到末尾返回 `io.EOF`。n > 0 和 err != nil 也可能同时出现，要先处理这 n 个字节，再看错误。

所以要“正好读满 n 个字节”，用 `io.ReadFull`：读不满就返回 `io.ErrUnexpectedEOF`。

`bufio.Reader` 在一个 Reader 外面加一层缓冲，默认 4096 字节。它一次从底层多读一些放进缓冲区，之后的小读取直接从缓冲区拿，减少系统调用的次数。它还提供了按分隔符读取的方法，比如 `ReadString('\n')`。

下面用 bufio 读一条 RESP 格式的请求，Mini-Redis 的协议就是这种格式：

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"strconv"
	"strings"
)

func main() {
	// 一条请求：数组有 2 个元素，第一个是 3 字节的 "GET"，第二个是 1 字节的 "k"
	r := bufio.NewReader(strings.NewReader("*2\r\n$3\r\nGET\r\n$1\r\nk\r\n"))

	header, _ := r.ReadString('\n') // "*2\r\n"
	count, _ := strconv.Atoi(strings.TrimSuffix(header[1:], "\r\n"))

	var args [][]byte
	for i := 0; i < count; i++ {
		line, _ := r.ReadString('\n') // "$3\r\n"
		size, _ := strconv.Atoi(strings.TrimSuffix(line[1:], "\r\n"))
		buf := make([]byte, size+2) // 内容加上结尾的 \r\n
		if _, err := io.ReadFull(r, buf); err != nil {
			fmt.Println("读不完整：", err)
			return
		}
		args = append(args, buf[:size])
	}
	fmt.Printf("%q\n", args)
}

// 输出：["GET" "k"]
```

这里为了看清结构，省略了错误处理和长度上限检查。真正的解析器每一步都要检查，下面的代码走读会看 [resp/parser.go](../../resp/parser.go) 的 `ReadRequest` 是怎样做的。

## 代码走读：resp 包

resp 包除了写包说明的 doc.go，还有三个实现文件，各管一件事：

| 文件 | 函数 | 做什么 |
|---|---|---|
| [parser.go](../../resp/parser.go) | `readHeader`、`ReadRequest` | 从 `bufio.Reader` 读出一条请求 |
| [request.go](../../resp/request.go) | `AppendRequest` | 把参数编码成一条请求。AOF 写日志、客户端发命令都用它 |
| [reply.go](../../resp/reply.go) | `EncodeReply`、`appendBulk` | 把执行结果编码成回复 |

### 1. readHeader：读一行头部

```go
func readHeader(reader *bufio.Reader) ([]byte, error) {
	line, err := reader.ReadSlice('\n')
	if errors.Is(err, bufio.ErrBufferFull) || len(line) > MaxHeaderLength {
		return nil, fmt.Errorf("protocol error: header exceeds %d bytes", MaxHeaderLength)
	}
	if err != nil {
		if err == io.EOF && len(line) == 0 {
			return nil, io.EOF
		}
		return nil, fmt.Errorf("protocol error: incomplete header: %w", err)
	}
	if len(line) < 3 || !bytes.HasSuffix(line, []byte("\r\n")) {
		return nil, errors.New("protocol error: header missing CRLF")
	}
	return line[:len(line)-2], nil
}
```

- 头部是 `*2\r\n`、`$3\r\n` 这样的短行。用 `ReadSlice` 而不是 `ReadString` 或 `ReadBytes`：后两个找不到 `\n` 时会一直扩容，客户端发来几个 GB 不带换行的数据，服务端就跟着分配几个 GB。`ReadSlice` 只在 4096 字节的缓冲区里找，找不到就返回 `bufio.ErrBufferFull`。
- `ReadSlice` 返回的是**缓冲区内部的一段视图**，只保证在下一次读之前有效，之后内容可能被覆盖（Go 八股 2 讲这个坑）。这里没出问题，是因为调用者拿到头部后马上用 `strconv.Atoi` 解析成数字，在下一次读之前就用完了。
- `line[:len(line)-2]` 去掉末尾的 `\r\n`。这是切片表达式，不拷贝。
- 只有“一个字节都没读到就遇到 EOF”才原样返回 `io.EOF`，表示连接干净地结束了。读到半行就断开，返回的是包装过的错误。第 06 章的 AOF 恢复要靠这个区别判断文件末尾是不是有半条记录。

### 2. ReadRequest：读一条完整的请求

```go
func ReadRequest(reader *bufio.Reader) ([][]byte, int, error) {
	line, err := readHeader(reader)
	// ……检查 *，解析出数组长度 length，检查 0 ≤ length ≤ MaxArrayLength
	used := len(line) + 2
	args := make([][]byte, length)
	for i := range args {
		header, err := readHeader(reader)
		// ……检查 $，解析出 size，检查 0 ≤ size ≤ MaxBulkLength
		used += len(header) + 2
		if size+2 > MaxRequestLength-used {
			return nil, 0, errors.New("protocol error: request exceeds byte limit")
		}
		used += size + 2
		content := make([]byte, size+2)
		if _, err := io.ReadFull(reader, content); err != nil {
			return nil, 0, fmt.Errorf("protocol error: incomplete bulk content: %w", err)
		}
		if content[size] != '\r' || content[size+1] != '\n' {
			return nil, 0, errors.New("protocol error: bulk content missing CRLF")
		}
		args[i] = content[:size]
	}
	return args, used, nil
}
```

和切片有关的几处：

- `make([][]byte, length)`：数组长度在头部已经知道，一次分配好外层切片，之后按下标填，不用 append。
- `make([]byte, size+2)` 加 `io.ReadFull`：内容的长度也已经知道，一次分配、一次读满。不管这些字节是一次到达还是分十次到达，`ReadFull` 都读满才返回。上面实验里的“半包”就是靠它等到后半条的。
- `args[i] = content[:size]`：去掉结尾的 `\r\n`，仍是切片表达式，不拷贝。每个参数都有自己单独分配的底层数组，互不共享。
- **分配之前先检查上限**。单个参数最多 16 MiB，参数最多 1024 个；但只检查这两条还不够，1024 × 16 MiB 就是 16 GiB。所以还有一个整条请求 32 MiB 的预算 `MaxRequestLength`，在每次 `make` 之前检查。
- 第二个返回值 `used` 是这条请求在线上实际占的字节数，AOF 恢复时用它算出“最后一条完整记录结束在文件的第几个字节”（第 06 章）。

### 3. AppendRequest 和 appendBulk：往切片后面追加

```go
func AppendRequest(dst []byte, args [][]byte) ([]byte, error) {
	// ……检查参数个数
	start := len(dst)
	data := append(dst, '*')
	data = strconv.AppendInt(data, int64(len(args)), 10)
	data = append(data, '\r', '\n')
	for _, arg := range args {
		// ……单个参数超过 16 MiB 就返回错误
		data = append(data, '$')
		data = strconv.AppendInt(data, int64(len(arg)), 10)
		data = append(data, '\r', '\n')
		// ……再加上这一段内容会让整条请求超过 32 MiB，就返回错误
		data = append(data, arg...)
		data = append(data, '\r', '\n')
	}
	return data, nil
}
```

- 函数名以 Append 开头、第一个参数是 `dst []byte`、返回追加后的切片，这是标准库的惯例，`strconv.AppendInt` 也是这样。调用者可以传 `nil`，也可以传一个已有的缓冲区接着往后写。
- 数字用 `strconv.AppendInt` 直接写进切片，不先转成字符串再拷贝一次。
- 两道检查的位置不同：单个参数的 16 MiB 上限在写 `$长度` 之前检查；整条请求的 32 MiB 预算在写完 `$长度\r\n`、追加内容之前检查，算的是这条请求所有参数加上 RESP 格式本身的字节。
- `start := len(dst)` 记下这条请求从哪里开始，整条请求的 32 MiB 预算只算这一条，不把 dst 里原有的内容算进去。
- 改造前，AOF 和客户端各有一份手写的编码代码。现在两边都调用这一个函数，编码规则只有一份。

回复的编码在 [reply.go](../../resp/reply.go) 里。bulk 回复由 `appendBulk` 写，写法和上面一样：`$`、长度、`\r\n`、内容、`\r\n`。

## Go 八股

### 八股 1：slice 的底层是什么？append 怎样扩容？

#### 一分钟口述版

> 切片底层是一个三字段的结构体：一个指向底层数组的指针、长度 len、容量 cap。切片本身很小，赋值和传参只拷贝这三个字段，底层数组是共享的。append 时如果容量够，就直接写进底层数组；容量不够就扩容：分配一个新数组，把旧数据拷过去，返回指向新数组的切片，所以一定要用返回值接住。扩容的规则是：需要的长度超过原容量的两倍，就直接用需要的长度；否则原容量小于 256 时翻倍，大于等于 256 时每次大约增加四分之一再加 192，从 2 倍平滑过渡到 1.25 倍。算出来以后，还要按内存分配器的规格向上取整，所以实际容量经常比公式算的大一点。

#### 要点

**底层结构**（`runtime/slice.go`）：

```text
type slice struct {
	array unsafe.Pointer // 指向底层数组
	len   int
	cap   int
}
```

**扩容规则**（`runtime/slice.go` 的 `nextslicecap`）：

1. 需要的长度 > 原容量 × 2：新容量直接等于需要的长度。
2. 原容量 < 256：新容量 = 原容量 × 2。
3. 原容量 ≥ 256：循环执行 `newcap += (newcap + 3*256) / 4`，直到够用。容量很大时，增长率趋近 1.25 倍。
4. 最后按内存分配器的大小规格（size class）向上取整，所以实际容量可能更大。

旧的八股文常说“小于 1024 翻倍，大于 1024 涨 1.25 倍”，那是 Go 1.18 之前的规则。Go 1.18 起改成了上面这个以 256 为界、平滑过渡的公式。

**亲手看一下扩容序列：**

```go
package main

import "fmt"

// 阻止编译器内联，让每次扩容都走运行时的 growslice，看到的才是运行时的规则。
//
//go:noinline
func add(s []int, v int) []int { return append(s, v) }

func main() {
	var s []int
	last := -1
	for i := 0; i < 2000; i++ {
		s = add(s, i)
		if cap(s) != last {
			fmt.Print(cap(s), " ")
			last = cap(s)
		}
	}
	fmt.Println()

	a := append([]int{1, 2, 3}, 4)
	fmt.Println(len(a), cap(a))
	b := append([]int(nil), 1, 2, 3, 4, 5)
	fmt.Println(len(b), cap(b))
}

// 输出：
// 1 2 4 8 16 32 64 128 256 512 848 1280 1792 2560
// 4 6
// 5 6
```

怎样读这些数字：
- 256 之前每次翻倍。
- 512 之后：按公式，512 + (512 + 768) / 4 = 832。一个 int 占 8 字节，832 个是 6656 字节，向上取整到分配器的 6784 字节这一档，所以实际容量是 848。
- `append([]int{1,2,3}, 4)`：3 翻倍是 6，正好落在一档上，容量是 6。
- `append(nil, 5 个元素)`：需要 5，超过 0 的两倍，按 5 算；5 个 int 是 40 字节，取整到 48 字节，所以容量也是 6。

> 如果去掉 `add`，直接在 main 里 append，你可能看到 `4 8 16…` 或 `1 2 3 4 8…`。这是因为较新的编译器发现切片不逃逸时，会先用栈上一块 32 字节的缓冲区作底层数组，不走堆分配。这是编译器的优化，不改变运行时的扩容规则。面试时被问“你测的和八股文不一样”，可以这样解释。

#### 项目里的例子

- **编码时往一个 `[]byte` 上 append**。[resp/reply.go](../../resp/reply.go) 的 `appendBulk` 和 [resp/request.go](../../resp/request.go) 的 `AppendRequest` 依次 append `$`、长度数字、`\r\n`、内容、`\r\n`；数字用 `strconv.AppendInt` 直接写进切片，不先转成字符串。
- **读请求时按长度一次分配**。[resp/parser.go](../../resp/parser.go) 的 `ReadRequest` 先读到 `$5\r\n`，知道内容有 5 个字节，就 `make([]byte, 5+2)`，再用 `io.ReadFull` 一次读满，不靠 append 一点点长大，也就不会触发扩容。

#### 常见追问

**追问 1：数组和切片有什么区别？**

数组长度固定，是类型的一部分，是值类型，赋值时拷贝全部元素。切片长度可变，本身只是一个三字段的描述符，赋值时只拷贝描述符，底层数组共享。

**追问 2：怎样避免频繁扩容？**

知道大概有多少元素时，用 `make([]T, 0, n)` 预先分配容量。

**追问 3：扩容后，原来的切片还能用吗？**

能用，但它指向的是旧数组。之后通过新切片做的修改，旧切片看不到，反过来也一样。这正是八股 2 讲的那个坑的另一面。

### 八股 2：两个切片共享底层数组，会出什么问题？

#### 一分钟口述版

> 切片表达式和赋值都不拷贝数据，多个切片可能指向同一个底层数组。这会带来两个问题。第一，修改一个切片的元素，另一个也会变。第二个更隐蔽：对一个子切片 append，如果它的容量还没用完，新元素会直接写进底层数组，覆盖掉原切片后面的数据；而一旦容量用完触发扩容，两个切片就分开了。所以 append 之后两个切片还共享不共享，取决于容量，代码的行为会随数据变化。解决办法是：需要独立的数据时显式拷贝；或者用三下标的切片表达式 `a[low:high:max]` 限制子切片的容量，让它下一次 append 一定会分配新数组。

#### 要点

```go
package main

import "fmt"

func main() {
	a := []int{1, 2, 3, 4, 5}
	b := a[1:3] // [2 3]，容量 4：可以一直延伸到 a 的末尾
	b = append(b, 99)
	fmt.Println(a) // a[3] 被覆盖了

	c := []int{1, 2, 3, 4, 5}
	d := c[1:3:3] // 三下标：容量限制为 3-1=2
	d = append(d, 99)
	fmt.Println(c, d) // d 扩容到了新数组，c 不受影响
}

// 输出：
// [1 2 3 99 5]
// [1 2 3 4 5] [2 3 99]
```

另外两个和共享有关的坑：
- **小切片拖住大数组。** 从一个 1 MB 的缓冲区里切出 10 字节保存下来，只要这个小切片还活着，整个 1 MB 的数组都不能被回收。需要长期保存的小片段，拷贝出来再存。
- **bufio 的 `ReadSlice`、`ReadLine` 返回的是缓冲区内部的视图**，下一次读取之后，内容可能被覆盖。要保存内容，必须拷贝。

#### 项目里的例子

这是 Mini-Redis 里最需要小心的地方：

- **引擎存值时必须拷贝。** 命令参数是调用者给的切片。如果引擎直接把它存进 map，调用者以后改了这块内存，存储里的值也会跟着变。[database/write.go](../../database/write.go) 的 `planWrite` 在一处统一拷贝 SET 和 LPUSH 的值，注释写的是“存进引擎的字节由引擎自己持有”。
  - 你可能会问：`ReadRequest` 每条请求都新分配内存，不拷贝好像也没事？问题是引擎不能假设调用者都这样做。测试、AOF 重放、以后别的调用者，都可能复用自己的缓冲区。
- **返回值也要拷贝。** GET 和 LRANGE 返回的是 `bytes.Clone` 的副本，而不是存储里那块内存本身。否则调用者改返回值，就改坏了存储。引擎自己从来不原地修改存进去的字节（SET 覆盖时是换上一个新切片），所以这次拷贝防的是调用者。
  - LPOP 是例外：弹出的值已经从链表上摘下来，引擎不再持有它，直接交给调用者就行，不用再拷贝。
- [database/engine_test.go](../../database/engine_test.go) 的 `TestEngineOwnsStoredAndReturnedBytes` 专门检查这两点：存进去以后改原切片、拿出来以后改返回值，存储里的值都不能变。动手实验 2 会把拷贝去掉，看它怎样失败。

#### 常见追问

**追问 1：函数里 append 一个传进来的切片，会影响调用者吗？**

分两种情况。容量够时，新元素写进了共享的底层数组，但调用者那份切片的 len 没变，看不到这个元素；如果调用者手里还有别的切片覆盖了这段位置，就会被悄悄改掉。容量不够时，函数里的切片指向了新数组，和调用者完全分开。

**追问 2：`for i, v := range s` 里修改 v，会改到切片吗？**

不会，v 是元素的拷贝。要修改，写 `s[i] = ...`。

### 八股 3：string 和 []byte 互相转换会拷贝吗？

#### 一分钟口述版

> 一般会拷贝。string 底层是一个指针加一个长度，而且不可变；[]byte 可以修改。如果转换时共用同一块内存，改 []byte 就会改到那个“不可变”的字符串，所以语言规定转换要拷贝。但编译器会在能证明安全的地方省掉拷贝：比如 []byte 转成 string 只是为了查 map 或做比较，用完就丢；或者 string 转成的 []byte 不逃逸、也从来不被修改。另外，结果很短又不逃逸时，会用栈上的小缓冲区，不在堆上分配。真要强制零拷贝，可以用 Go 1.20 加入的 `unsafe.String` 和 `unsafe.Slice`，但那样就要自己保证转换后谁都不再修改这块内存，一般业务代码不该这么做。

#### 要点

**底层结构**（`runtime/string.go`）：

```text
type stringStruct struct {
	str unsafe.Pointer
	len int
}
```

string 只有指针和长度，没有容量，也不能修改。所以子串 `s[a:b]` 可以放心地共享内存，不需要拷贝。

**编译器省掉拷贝的常见情况：**

| 写法 | 为什么不用拷贝 |
|---|---|
| `m[string(b)]` 查 map | 查完就丢，不会保存这个字符串 |
| `string(b) == "PING"`，以及 switch 比较 | 只读一下 |
| `for i, c := range []byte(s)` | 只读 |
| `b := []byte(s)`，b 不逃逸且从不修改 | 编译器直接复用字符串的内存（`go build -gcflags=-m` 会打印 `zero-copy string->[]byte conversion`） |
| 结果不逃逸且不超过 32 字节 | 用栈上的临时缓冲区，不在堆上分配（拷贝本身还在） |

**注意**：用 `m[string(b)] = v` **写入** map 时，key 要长期保存，一定会拷贝。

#### 项目里的例子

- 引擎的 map 用 `string` 作 key，参数却是 `[]byte`，所以到处都有 `key := string(args[1])`。key 要存进 map，这次拷贝省不掉，也不该省：它正好让存储不依赖调用者的内存。
- 命令名的比较：`strings.ToUpper(string(args[0]))` 之后在 switch 里比较。ToUpper 会产生新字符串，这次分配不是转换造成的。
- 这是一个用简单换安全的取舍：每条命令有几次小拷贝，但存储和网络缓冲区之间不会出现共享内存的 bug。

#### 常见追问

**追问 1：字符串为什么要设计成不可变？**

不可变的字符串可以随意共享：子串不用拷贝，作 map 的 key 不怕被改，多个 goroutine 同时读也不需要加锁。

**追问 2：怎样确认某个转换有没有拷贝？**

用 `go build -gcflags=-m` 看编译器的逃逸分析输出；或者写一个 benchmark，加 `-benchmem` 看每次操作分配了几次内存（第 08 章）。

### 八股 4：nil 切片和空切片有什么区别？

#### 一分钟口述版

> nil 切片是 `var s []int`，指针是 nil；空切片是 `[]int{}` 或 `make([]int, 0)`，指针不是 nil，但长度是 0。在绝大多数操作上两者一样：len 都是 0，都能 append，都能 range。区别主要在两处：`s == nil` 的结果不同；用 encoding/json 编码时，nil 切片变成 `null`，空切片变成 `[]`。所以对外的 API 要返回“空列表”时，最好返回空切片。

#### 要点

```go
package main

import (
	"encoding/json"
	"fmt"
)

func main() {
	var a []int
	b := []int{}
	fmt.Println(a == nil, b == nil, len(a), len(b))

	ja, _ := json.Marshal(a)
	jb, _ := json.Marshal(b)
	fmt.Println(string(ja), string(jb))
}

// 输出：
// true false 0 0
// null []
```

#### 项目里的例子

- RESP 协议也有类似的区分：空值 `$-1\r\n`（key 不存在）和空字符串 `$0\r\n\r\n`（key 存在，值是空的）是两种不同的回复。[resp/reply.go](../../resp/reply.go) 的 `EncodeReply` 用 `nil` 表示前者、用长度为 0 的 `[]byte` 表示后者，这两种在 Go 里本来就能区分开。
- LRANGE 返回空列表时，回复是 `*0\r\n`，不是空值。

#### 常见追问

**追问：判断切片是否为空，应该写 `s == nil` 还是 `len(s) == 0`？**

写 `len(s) == 0`，它对 nil 切片和空切片都成立。

### 配角：TCP 粘包和半包

#### 一分钟口述版

> TCP 提供的是字节流，不是一条一条的消息。发送方连续写了两条请求，接收方一次 Read 可能把两条一起读到，这叫粘包；也可能只读到半条，这叫半包。这不是 TCP 的错，而是因为它本来就没有消息边界，边界要由应用层的协议来定。常见的做法有三种：固定长度、用分隔符、在消息前面加上长度。RESP 是后两种的结合：每一行用 `\r\n` 结束，二进制内容前面先写长度，读的时候按长度读，所以内容里有 `\r\n` 也不会出错。

#### 项目里的例子

- 解析器先读到 `$5\r\n`，再用 `io.ReadFull` 精确读 5 + 2 个字节。不管这些字节是一次到达还是分十次到达，`ReadFull` 都会读满才返回。这就解决了半包。
- 一次 Read 读进来的多余字节留在 `bufio.Reader` 的缓冲区里，下一次读请求时接着用。这就解决了粘包。客户端一次发多条命令（流水线），靠的也是这一点。
- [server/testdata/session.golden](../../server/testdata/session.golden) 是一份完整会话的回复字节，由 [server/golden_test.go](../../server/golden_test.go) 逐字节比对。它专门覆盖了“值里含 `\r\n` 和 `\x00`”和“一次写入多条请求”这两种情况。

## 关键设计与为什么

**1. 先检查上限，再分配内存。**
- 服务端按客户端写的长度去 `make`。如果不先检查，一行 `$999999999\r\n` 就能让服务端分配近 1 GB。
- 三道上限：单个参数 16 MiB、参数个数 1024、整条请求 32 MiB。头部本身也限制在 64 字节以内。
- 放弃了什么：超过 16 MiB 的单个值存不进来，一条请求所有参数加起来也不能超过 32 MiB。真实的 Redis 默认允许单个值到 512 MB（`proto-max-bulk-len`）。Mini-Redis 是学习项目，选择了更保守的上限。

**2. 读头部用 `ReadSlice`，不用 `ReadString`。**
- `ReadString` 用起来更方便，返回的字符串也可以放心保存。但它找不到换行就一直扩容，遇到恶意输入会占满内存。
- `ReadSlice` 受缓冲区大小限制，代价是返回值只是缓冲区的视图，必须在下一次读之前用完。代码里马上把它解析成数字，满足这个条件。

**3. 读请求是同步的：调用一次，读一条。**
- `ReadRequest` 不启动 goroutine，也不用 channel。连接的处理循环是“读一条、执行、写回”，AOF 恢复是“读一条、重放”，两边都直接调用它。
- 早期的版本不是这样：解析放在一个单独的 goroutine 里，通过 channel 把结果送出来。为什么改掉，第 07 章讲。

**4. 引擎持有自己存的字节。**
- 在写入的入口统一拷贝一次，读出时再拷贝一次。这样存储和网络缓冲区之间不共享任何内存，谁改了自己的切片都影响不到别人。
- 代价是每条命令多几次小的内存分配。和网络 IO、写日志刷盘相比，这点开销可以忽略。

**实验 1：亲眼看 `ReadSlice` 的结果被覆盖。**

```go
package main

import (
	"bufio"
	"fmt"
	"strings"
	"testing/iotest"

func main() {
	// OneByteReader 每次只给 1 个字节，模拟数据一点点到达的网络连接
	r := bufio.NewReader(iotest.OneByteReader(strings.NewReader("first\nsecond\n")))

// "first\n"
// "second" "second\n"
```

第二次读的时候，缓冲区里已经没有未读的数据，bufio 从缓冲区开头重新填数据，正好盖住了 `a` 指向的那几个字节。要是缓冲区里本来就有第二行，不需要重新填，`a` 也可能碰巧保持原样，所以文档只保证“下一次读之前有效”，不能依赖它之后的内容。如果把 `a` 存进 map，存进去的值就会悄悄变掉。想保存，就用 `bytes.Clone(a)`。

## 常见误区

- **以为切片表达式会拷贝。** `b := a[1:3]` 只是新建一个视图，改 b 就是改 a。
- **append 后不接返回值。** `append(s, x)` 单独写一行，结果就丢掉了。编译器会报 “value not used”。
- **把 `len(s)` 当成字符数。** 它是字节数，中文一个字通常占 3 个字节。
- **用 `s[i]` 取“第 i 个字符”。** 它取的是字节。按字符处理要用 `range` 或先转成 `[]rune`。
- **保存了 bufio `ReadSlice` 的结果。** 它指向缓冲区内部，下一次读就被覆盖。
- **以为一次 Read 就能读到一整条消息。** 网络上的 Read 读到多少都有可能，必须按协议的边界来读。

## 自测

**1. `readHeader` 为什么用 `ReadSlice`？它返回的切片有什么要小心的？**

<details><summary>答案</summary>

`ReadSlice` 只在 bufio 的固定缓冲区里找换行，找不到就返回 `ErrBufferFull`，不会因为恶意的超长输入无限扩容。它返回的是缓冲区内部的视图，下一次读就可能被覆盖，所以必须在下一次读之前用完；代码里马上用 `strconv.Atoi` 把它解析成数字。

</details>

**2. 一条请求分三次到达，`ReadRequest` 怎样把它读完整？多条请求一次到达呢？**

<details><summary>答案</summary>

分三次到达：头部用 `ReadSlice` 读到换行为止，内容用 `io.ReadFull` 按长度读满，两者都会等数据到齐才返回。一次到达多条：bufio 一次读进来的多余字节留在缓冲区，下一次调用 `ReadRequest` 接着从缓冲区读。

</details>

**3. 只限制单个参数 16 MiB、参数个数 1024 够不够？代码里还做了什么？**

<details><summary>答案</summary>

不够，两者相乘是 16 GiB。代码还有一个整条请求 32 MiB 的预算，每次 `make` 之前检查“已经用掉的字节数加上这一段”是否超标。

</details>

**4. `planWrite` 为什么要拷贝 SET 和 LPUSH 的值？GET 为什么返回副本？LPOP 为什么不用？**

<details><summary>答案</summary>

参数切片属于调用者，调用者以后可能修改或复用这块内存，引擎必须存自己的一份。GET 返回副本，是为了防止调用者修改返回值时改坏存储。LPOP 弹出的值已经从链表上摘下，引擎不再持有，直接交出去就行。

</details>

**5. 下面的代码打印什么？**

```text
a := []int{1, 2, 3, 4, 5}
b := a[1:3]
b = append(b, 99)
fmt.Println(a)
```

<details><summary>答案</summary>

`[1 2 3 99 5]`。b 的容量是 4，append 没有扩容，直接写进了和 a 共享的底层数组，覆盖了 `a[3]`。写成 `a[1:3:3]` 就能避免。

</details>

**6. `ReadRequest` 返回的 `size` 是干什么用的？为什么不能用参数重新编码一遍来算？**

<details><summary>答案</summary>

`size` 是这条请求在线上实际占的字节数。AOF 恢复时用它累加出“最后一条完整记录结束的位置”，发现半条记录时截断到这里。重新编码不一定和原来的字节完全一样，比如长度写成了 `$03` 这种带前导零的形式，所以只能用实际读到的字节数。

</details>

## 开发过程回放

以下按 git 历史整理。

- **2026-05-20，`2343d6e`，流式解析。** 解析器改成 `ParseStream`：每个连接起一个 goroutine 负责解析，通过 channel 把解析结果（`Payload`）送给处理函数。读头部用的是 `ReadBytes('\n')`。
- **2026-08-06，`c9d3081`，加上长度上限。** 新增 `MaxArrayLength = 1024` 和 `MaxBulkLength = 16 << 20` 两个常量。
- **2026-08-22，`a67cec9`，长度校验收紧。** 负数和超限的长度都按协议错误处理，同时加入了第一个模糊测试（第 08 章）。
- **2026-10-01，`3d95ea3`，第一阶段完成。** 解析器补上了整条请求 32 MiB 的预算和 64 字节的头部上限，读头部从 `ReadBytes` 改成 `ReadSlice`，代码里的注释写明了原因：`ReadBytes` 会随恶意的无换行输入扩容。同时新增“返回实际字节数”的测试，给 AOF 截断用。
- **2026-11-10，PR #5，可读性改造。**
  - `ParseStream` 的“goroutine 加 channel”改成同步的 `ReadRequest`。上限检查、CRLF 检查和错误分类原样保留，原有的解析器测试全部改成调用 `ReadRequest`，模糊测试 `FuzzParseStream` 改名为 `FuzzReadRequest`。
  - AOF 和客户端各自的请求编码合并成 `AppendRequest`。
  - 修好了客户端的一个真实 bug：它原来只读回复的第一行，LRANGE 返回数组时，后面的元素留在缓冲区里，下一条命令读到的是上一次的残留。现在 [cmd/client/reply.go](../../cmd/client/reply.go) 按类型把每种回复读完整。
