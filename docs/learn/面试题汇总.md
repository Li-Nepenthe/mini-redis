## 一、调度与 goroutine

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| 讲讲 GMP 调度模型 | G 是 goroutine，M 是线程，P 是执行许可证（个数 = GOMAXPROCS）；每个 P 一个 256 的本地队列 + 全局队列；本地 → 全局 → 网络轮询器 → 偷一半 | 02 八股 1 |
| 为什么要有 P | Go 1.1 之前所有 M 抢一个全局队列的锁；P 让大部分调度在本地完成 | 02 八股 1 |
| goroutine 和线程有什么区别 | 栈 2 KB 起可伸缩 vs MB 级固定；用户态切换 vs 内核切换；运行时调度 vs 操作系统调度 | 02 八股 1 追问 1 |
| GOMAXPROCS 越大越好吗 | 不是，超过核数只增加切换；Go 1.25 起在 Linux 上参考 cgroup 配额 | 02 八股 1 追问 2 |
| 死循环会卡住其他 goroutine 吗 | Go 1.14 起不会：运行超过 10 ms 被异步抢占 | 02 八股 1 追问 3 |
| goroutine 阻塞在网络读上会怎样 | 非阻塞 socket 返回 EAGAIN → 挂到网络轮询器 → M 去跑别的 G → 就绪后放回队列 | 02 八股 2 |
| 读文件和读网络对调度器有什么不同 | 文件 IO 是真阻塞的系统调用，M 被卡住，sysmon 把 P 交给别的 M | 02 八股 2 追问 1 |
| goroutine 里 panic 了会怎样 | 没被 recover 就整个进程退出（退出码 2）；recover 只管同一个 goroutine | 02 八股 3 |
| 一个连接一个线程为什么扛不住 | 线程栈大、切换贵（C10K）；事件循环高效但难写；Go 两者兼得 | 02 配角 |

## 二、并发原语

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| Mutex 怎样实现？正常模式和饥饿模式 | 状态字 + 信号量；CAS 快速路径 → 自旋 → 排队；等待超过 1 ms 进入饥饿模式，直接交给队头 | 04 八股 1 |
| Mutex 可重入吗？能复制吗 | 都不能；复制锁用 go vet 的 copylocks 检查 | 04 Go 基础 1 |
| RWMutex 适合什么场景？为什么不能升级、不能递归读锁 | 读多写少；写者优先，有写者排队时新读者要等，所以递归读锁和升级都会死锁；只能放读锁、加写锁、**重新检查** | 04 八股 2 |
| defer 的执行顺序、参数求值、修改返回值、开销 | 后进先出；参数在 defer 时求值；能改命名返回值；Go 1.14 起开放编码，几乎零开销 | 04 八股 3 |
| 死锁怎样产生、怎样避免 | 四个必要条件，实际能破坏的是“环”：全局统一加锁顺序；运行时只能发现全局死锁 | 04 八股 4 |
| 锁和 channel 怎么选 | 保护共享状态用锁；传递所有权和事件用 channel | 04 八股 4 追问 |
| channel 底层 | hchan：锁 + 环形缓冲区 + 发送和接收两个等待队列；有人等就直接拷到对方栈上 | 07 八股 1 |
| 有缓冲和无缓冲的区别 | 无缓冲是同步握手；有缓冲允许速度暂时不一致 | 07 八股 1 |
| 关闭的 channel、nil channel 的读写关 | nil：读写永久阻塞、关闭 panic；已关闭：读到零值和 false、写 panic、再关 panic | 07 八股 2 |
| 多个发送方怎样安全关闭 channel | 谁都不关，或者等所有发送方结束后由一个专门的 goroutine 关；用 context 通知停止 | 07 八股 2 追问 |
| goroutine 泄漏怎样产生、怎样排查 | 永远阻塞在 channel、锁、无超时的 IO 上；NumGoroutine、goroutine profile、Go 1.27 的 goroutineleak profile | 07 八股 3 |
| context 有什么用？取消怎样传递 | 一棵树，取消从上往下传，关闭 Done channel 广播；一定调用 cancel；它只是通知 | 07 八股 4 |
| WaitGroup 的坑 | Add 必须在 go 之前；Go 1.25 起用 wg.Go；`go vet` 的 waitgroup 检查 | 07 Go 基础 3 |
| 怎样实现优雅停机 | 信号 → 关监听 → 执行中的做完、空闲的关掉、没开始的不做 → 带超时等待 → 按依赖反方向释放 | 07 八股 5 |
| 什么时候不该用 channel | 严格顺序的两件事，拆成两个 goroutine 只会增加关闭、取消、排空的复杂度 | 07 配角 |
| 什么时候用 atomic | 只保护一个变量的一次操作；多步复合操作还是要锁 | 04 Go 基础 4 |

## 三、数据结构

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| slice 的底层 | 指针 + len + cap；赋值传参只拷贝这三个字段 | 01 八股 1 |
| append 怎样扩容 | 超过两倍直接用需要的长度；256 以下翻倍；之后平滑过渡到 1.25 倍；再按分配器规格向上取整 | 01 八股 1 |
| 共享底层数组的坑 | 子切片 append 可能覆盖原切片的数据；用拷贝或三下标切片 `a[i:j:k]` 避免 | 01 八股 2 |
| string 和 []byte 互转会拷贝吗 | 一般会；编译器在查 map、比较、不逃逸且不修改等情况下省掉 | 01 八股 3 |
| nil 切片和空切片 | 大部分操作一样；`== nil` 和 JSON 编码（null vs []）不同 | 01 八股 4 |
| map 的底层（Go 1.24 起） | Swiss Table：8 槽一组 + 控制字（H2 低 7 位）一次比较 8 个；单表最多 1024 槽，满了翻倍或拆分 | 03 八股 1 |
| map 的旧实现 | 桶（8 个 key + tophash）+ 溢出桶；负载 6.5 扩容；渐进式搬迁 | 03 八股 1 |
| map 为什么无序 | 遍历起点随机，有意不让人依赖顺序 | 03 八股 1 |
| map 的 value 能取地址吗 | 不能，扩容会搬动元素 | 03 八股 1 追问 1 |
| map 并发写为什么崩？怎样解决 | 运行时检测到并发写直接 fatal（recover 接不住）；加锁、sync.Map 或分片 | 03 八股 2 |
| sync.Map 适合什么 | 读多写少，或各 goroutine 的 key 基本不重叠；复合操作仍要加锁 | 03 八股 2 |
| 结构体内存对齐、空结构体 | 字段顺序影响大小；`struct{}` 大小为 0，用作集合的值和信号 | 03 Go 基础 5 |

## 四、接口与类型

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| interface 的底层 | eface（类型 + 数据）和 iface（itab + 数据）；itab 里有方法地址表 | 03 八股 3 |
| nil 指针赋给接口为什么不等于 nil | 类型那一半不是 nil；没有错误时直接 `return nil` | 03 八股 3 |
| 值接收者和指针接收者怎么选 | 要修改、含锁、结构大用指针；指针接收者的方法只有 `*T` 能满足接口 | 03 八股 4 |
| Go 有继承吗 | 没有，用嵌入复用代码，用接口实现多态；嵌入的方法不知道外层类型 | 03 Go 基础 2；00 八股 3 追问 1 |
| 隐式实现有什么好处 | 接口由使用方定义，提供方不用 import；两个包互不依赖也能对上 | 03 八股 3 项目例子 |
| new 和 make 的区别 | new 任何类型返回零值指针；make 只用于 slice、map、chan，返回初始化好的值本身 | 00 八股 1 |
| Go 只有值传递吗 | 是；slice、map、chan 的值本身含指针，所以看起来像引用 | 00 八股 2 |
| 循环变量的坑，Go 1.22 改了什么 | 以前整个循环一个变量，闭包都引用它；1.22 起每次迭代一个新变量，由 go.mod 的版本决定 | 00 八股 4 |

## 五、内存与 GC

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| Go 的 GC 怎样工作 | 并发标记清除，三色标记；混合写屏障防止漏标；两次很短的 STW | 05 八股 1 |
| 为什么需要写屏障 | 并发标记时，黑色对象新指向白色对象、且灰色路径被删，白色对象会被漏标 | 05 八股 1 |
| GC 什么时候触发 | 堆到达目标（存活堆 + (存活堆 + 栈 + 全局) × GOGC/100）；2 分钟强制；手动 | 05 八股 2 |
| GOGC 和 GOMEMLIMIT 怎样调 | GOGC 用内存换 CPU；GOMEMLIMIT 是软上限，容器里设成限制的九成左右 | 05 八股 2 |
| 什么是逃逸分析 | 编译器证明函数返回后不再使用就放栈上，否则放堆上；`-gcflags=-m` 查看 | 05 八股 3 |
| 删了数据内存为什么不降 | 数据结构不缩小、GC 还没跑、运行时留着复用、RSS 指标；`debug.FreeOSMemory` 立刻归还 | 05 八股 4 |
| Timer 和 Ticker，Go 1.23 改了什么 | 未 Stop 的计时器也能被回收；channel 改为同步，Stop/Reset 后不会收到旧值 | 05 八股 5 |
| select 多个就绪选哪个 | 均匀随机；nil channel 的 case 永远不就绪 | 05 Go 基础 3 |

## 六、错误处理

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| Go 为什么没有 try/catch | 错误是值，在发生的地方就地处理；panic 只给真正的程序错误 | 06 八股 1 |
| errors.Is 和 errors.As | Is 找特定的值（哨兵错误）；As 找特定的类型并取出来；Go 1.26 有 AsType | 06 八股 2 |
| `%w` 和 `%v` | `%w` 保留错误链，并把内部错误变成 API 的一部分；`%v` 只拼文字 | 06 八股 2 |
| 什么时候用 panic？recover 能接住所有 panic 吗 | 程序员错误、初始化失败；fatal error 和别的 goroutine 的 panic 接不住 | 06 八股 3 |
| 怎样写平台相关的代码 | 文件名后缀或 `//go:build`；每个平台恰好一个实现；`GOOS=darwin go vet` 检查 | 06 Go 基础 5 |

## 八、网络、操作系统与 Redis

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| TCP 粘包和半包 | TCP 是字节流没有边界；靠协议定边界：定长、分隔符、长度前缀；RESP 是分隔符 + 长度前缀 | 01 配角 |
| fsync 是什么 | write 只到页缓存；fsync 返回成功才算写到磁盘 | 06 八股 4 |
| fsync 失败能重试吗 | 不能简单重试，脏页可能已被标成干净；正确做法是停止接受写入 | 06 八股 4 |
| 每条写都 fsync 太慢怎么办 | 组提交：一批写一次 fsync | 06 八股 4 追问 1 |
| Redis 的 AOF 和 RDB | AOF 记命令，恢复慢、丢得少；RDB 存快照，恢复快、丢得多；everysec 是折中；4.0 起可混合 | 06 八股 4 |
| Redis 为什么单线程 | 瓶颈在网络不在 CPU；无锁、命令天然原子；6.0 起多线程做网络 IO，命令仍单线程 | 04 配角 |
| Redis 怎样删除过期 key | 惰性删除 + 定期随机抽样（比例高就继续、有时间上限）+ 内存淘汰兜底 | 05 配角 |
| Redis 的数据结构 | String 是 SDS；List 是 quicklist（listpack 连成的链表）；dict 渐进式 rehash | 03 配角；03 八股 1 追问 3 |
| 分片锁为什么能提升性能，热点 key 呢 | 分片减少不同 key 之间的锁竞争；热点 key 都落在一个分片，分片无效 | 04 配角 |

## 九、关于这个项目

面试官问“介绍一下你的项目”“你在里面做了什么取舍”时用。

| 问题 | 一句话要点 | 出处 |
|---|---|---|
| 一条命令从进来到回复，经过了哪些地方 | server 的 `handle` 用 `ReadRequest` 读 → `Engine.Exec` 分发 → 写命令先日志后内存 → `EncodeReply` → 写回 | 00 代码走读 |
| 包是怎样划分的 | database 不依赖任何项目包；日志和网络都通过只有一个方法的接口接进来；`cmd/server` 负责组装 | 00 关键设计；03 代码走读 4 |
| 怎样保证“回复了 OK 的写入不会丢” | 先在锁内算出写计划，日志写入并 fsync 成功后才改内存；每条写都 fsync | 06 代码走读 1；06 关键设计 1 |
| AOF 为什么不原样记录命令 | 记效果：EXPIRE 记绝对到期时刻，新建列表记 `_LNEW`，无效果的写不记；否则重放结果和运行时不一致 | 06 关键设计 2 |
| AOF 文件末尾坏了怎么办 | 半条记录截断后继续启动；完整的坏记录拒绝启动，避免悄悄丢掉后面已确认的数据 | 06 关键设计 3 |
| 磁盘写失败以后怎么办 | 截断回最后确认的位置，之后一直拒写，不重试 fsync | 06 代码走读 2 |
| 多 key 命令怎样避免死锁 | 换算成分片编号，去重、排序后加锁，倒序解锁；`logMu` 永远在分片锁之前 | 04 代码走读 1 |
| 读的时候发现 key 过期了怎么办 | 读锁不能升级：放读锁、加写锁、按当前时间重新检查再删、回头重新读 | 04 代码走读 2 |
| 开启 AOF 后分片还有用吗 | 对写几乎没用（都排在 `logMu` 上）；对读仍然有用 | 04 关键设计 4 |
| 过期的 key 怎样删除，内存怎样归还 | 惰性删除 + 每 250 ms 每分片最多抽 256 个；累计删 32768 个且间隔 5 秒以上，锁外调用 `FreeOSMemory` | 05 代码走读；05 关键设计 |
| 优雅停机怎样做 | 以“开始执行”为界；停机检查和标记执行在同一把锁里；关闭空闲连接打断 Read；2 秒超时如实报告 | 07 代码走读；07 关键设计 |
| 为什么去掉了每个连接的解析 goroutine | 读和执行本来就是顺序的；多一个 goroutine 就多一套关闭、取消、排空，停机字段从 18 个减到 8 个 | 07 配角 |
| 1000 个连接要多少线程 | 实测 14 个：空闲连接挂在网络轮询器上，不占线程 | 02 动手实验 |
| 你怎样证明重构没有改变行为 | 改代码前先录三份 golden 并逐字节对比；再故意改坏代码检验测试，补上了 4 处测试漏洞 | 08 配角 |
| 分片带来了多少提升？你怎么测的 | 读多写少时 1 个分片约 390 ns/op，16 个约 60 ns/op；比较两个版本要在同一时段交替运行 | 04 配角；08 八股 2 |
| 这个项目有哪些没做的 | 没有组提交（每条写都 fsync）、没有 AOF 重写、没有内存淘汰、没有连接数上限、只支持 10 条命令 | 06 八股 4 追问 1；05 配角；02 关键设计 4 |
