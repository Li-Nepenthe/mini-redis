## Go 基础

### 1. sync.Mutex

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex // 零值就是一把没锁上的锁，不需要初始化
	n  int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock() // 加锁后立刻 defer 解锁，函数从哪里返回都不会忘
	c.n++
}

func main() {
	var c Counter
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(c.Inc)
	}
	wg.Wait()
	fmt.Println(c.n)
}

// 输出：1000
```

去掉 `Lock` 和 `Unlock`，结果通常小于 1000：`c.n++` 不是一步完成的，而是“读出来、加一、写回去”三步，两个 goroutine 可能读到同一个旧值。用 `go run -race` 运行，竞态检测器会直接指出冲突的那两行（第 08 章）。

**三条规则：**
- **第一次使用以后不能复制。** 锁的状态存在结构体字段里，复制一份就是一把独立的新锁。含锁的结构体要用指针传递，方法用指针接收者。`go vet` 会检查这种错误：

  ```go
  func show(c Counter) { ... } // go vet：show passes lock by value: Counter contains sync.Mutex
  ```

- **不可重入。** 同一个 goroutine 对一把已经锁上的 Mutex 再调用 `Lock`，会永远等下去。
- **对没锁上的 Mutex 调用 `Unlock`，是 fatal error**，程序直接退出，recover 接不住。

### 2. sync.RWMutex

读写锁允许多个读者同时持有读锁；写锁是独占的，有写者时读者和其他写者都要等。

```go
type Cache struct {
	mu   sync.RWMutex
	data map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.data[k]
	return v, ok
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[k] = v
}
```

### 3. defer

`defer f()` 把调用 f 推迟到当前函数返回之前执行。三条规则：

```go
package main

import "fmt"

func order() {
	for i := range 3 {
		defer fmt.Print(i, " ") // 规则 1：后进先出
	}
}

func args() {
	x := 1
	defer fmt.Println("defer 时的 x =", x)          // 规则 2：参数在 defer 语句执行时就求值
	defer func() { fmt.Println("闭包里的 x =", x) }() // 闭包读的是返回时的 x
	x = 2
}

func named() (result int) {
	defer func() { result *= 10 }() // 规则 3：defer 能修改命名返回值
	return 5                        // 先把 result 设成 5，再执行 defer
}

func main() {
	order()
	fmt.Println()
	args()
	fmt.Println(named())
}

// 输出：
// 2 1 0
// 闭包里的 x = 2
// defer 时的 x = 1
// 50
```

### 4. sync/atomic

对一个整数做简单的加减、读写，可以用原子操作代替锁。Go 1.19 起有类型化的写法，比旧的函数式写法更不容易用错：

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var hits atomic.Int64
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(func() { hits.Add(1) })
	}
	wg.Wait()
	fmt.Println(hits.Load())
}

// 输出：1000
```

原子操作只能保护**一个变量的一次操作**。要让“检查一个值，再根据它改另一个值”这样的几步整体不被打断，还是要用锁。

## 代码走读：引擎里的三种加锁方式

先看全貌，每条命令拿什么锁：

| 命令 | 怎样加锁 | 在哪里 |
|---|---|---|
| GET、LRANGE、TTL | 一个分片的读锁，经 `lockRead` | [read.go](../../database/read.go)、[expire.go](../../database/expire.go) |
| EXISTS | 涉及的所有分片的写锁，经 `lockKeys` | [read.go](../../database/read.go) |
| SET、LPUSH、LPOP、DEL、EXPIRE | 开了 AOF 时先拿 `logMu`，再拿涉及的分片的写锁 | [write.go](../../database/write.go) |
| 后台清理 | 逐个分片拿写锁，抽查完就放 | [expire.go](../../database/expire.go) |

### 1. lockKeys：多个 key，按编号加锁

[database/shard.go](../../database/shard.go)：

```go
func (e *Engine) lockKeys(keys [][]byte, write bool) func() {
	seen := make(map[int]bool, len(keys))
	indices := make([]int, 0, len(keys))
	for _, key := range keys {
		index := int(fnv32(string(key)) & (e.shardCount - 1))
		if !seen[index] {
			seen[index] = true
			indices = append(indices, index)
		}
	}
	sort.Ints(indices)
	for _, i := range indices {
		if write {
			e.shards[i].mu.Lock()
		} else {
			e.shards[i].mu.RLock()
		}
	}
	return func() {
		for i := len(indices) - 1; i >= 0; i-- {
			if write {
				e.shards[indices[i]].mu.Unlock()
			} else {
				e.shards[indices[i]].mu.RUnlock()
			}
		}
	}
}
```

三件事，各防一种错误：

- **去重**（`seen`）：`DEL a b` 里 a 和 b 可能在同一个分片，同一把锁加两次，第二次会永远等第一次释放。Mutex 不可重入。
- **排序**（`sort.Ints`）：所有命令都按分片编号从小到大加锁，等待关系就不会成环（八股 4）。
- **返回解锁函数**：调用者写 `defer unlock()`，加锁和解锁写在相邻两行，不会忘。解锁时倒序，和加锁正好相反。

### 2. lockRead：读锁不能升级时怎么办

[database/expire.go](../../database/expire.go)：

```go
func (e *Engine) lockRead(key string) (*shard, time.Time) {
	s := e.getShard(key)
	for {
		s.mu.RLock()
		now := e.now()
		entry, ok := s.expires[key]
		if !ok || now.Before(entry.deadline) {
			return s, now
		}
		s.mu.RUnlock()
		s.mu.Lock()
		s.purgeExpired(key, e.now())
		s.mu.Unlock()
	}
}
```

- 大多数时候 key 没有过期，拿到读锁、检查一下就返回，**返回时仍然持有读锁**，调用者负责 `defer s.mu.RUnlock()`。
- key 过期了，就要删掉它，这要写锁。RWMutex 不能把读锁升级成写锁，只能先放读锁、再加写锁。
- 加上写锁以后，`purgeExpired` **按当前时间重新检查**一次：中间别的连接可能已经用 SET 写了一个新值，新值没过期，就不能删。
- 删完放掉写锁，回到循环开头重新拿读锁，再看一遍。这一次 key 已经不存在，或者是别人刚写的新值，都会直接返回。

### 3. executeWrite：两层锁的顺序

[database/write.go](../../database/write.go)：

```go
if e.log != nil {
	e.logMu.Lock()
	defer e.logMu.Unlock()
}
keys := writeKeys(args, cmd)
unlock := e.lockKeys(keys, true)
defer unlock()
```

- 第一层是全局的 `logMu`，只在开了 AOF 时才拿。它让写日志的顺序和修改内存的顺序一致：写命令一条一条地排队写日志，重启时按日志重放，得到的就是和运行时一样的状态。
- 第二层是涉及的分片的写锁，一直持有到内存改完。
- 顺序永远是先 `logMu` 后分片锁，没有任何代码反过来。
- 代价：开了 AOF 时，所有写命令在 `logMu` 上排成一队，fsync 期间谁也写不了。分片带来的写并行，在开启 AOF 后就没有了。读命令不拿 `logMu`，不受影响，除非它要读的分片正被一条写命令锁着。

## Go 八股

### 八股 1：sync.Mutex 是怎样实现的？正常模式和饥饿模式是什么？

#### 一分钟口述版

> Mutex 的核心是一个 32 位的状态字，加一个信号量。状态字的低三位分别表示“已上锁”“有等待者被唤醒了”“处于饥饿模式”，其余的位记录等待者的数量。加锁时先用一次 CAS 把状态从 0 改成“已上锁”，成功就直接返回，这是最快的路径。失败了，在多核、而且还有别的 P 在运行时，会先自旋几次，因为锁很可能马上就被释放了；还拿不到，就在信号量上排队睡眠。Mutex 有两种模式。正常模式下，被唤醒的等待者要和新来的 goroutine 抢锁，新来的正在 CPU 上运行，往往抢得赢，这样吞吐量高，但排队的可能一直抢不到。所以一个等待者醒来后发现自己已经等了超过 1 毫秒、锁还被别人占着，就把锁切换到饥饿模式（没有定时器到点自动切换，要等这个等待者醒来时判断）：解锁时直接把锁交给队头的等待者，新来的不抢也不自旋，直接排到队尾。等到队里只剩它一个、或者它等待的时间不到 1 毫秒，再切回正常模式。

#### 要点

**状态字**（`internal/sync/mutex.go`）：

| 位 | 含义 |
|---|---|
| `mutexLocked`（第 0 位） | 已上锁 |
| `mutexWoken`（第 1 位） | 已经有一个等待者被唤醒，正在抢锁。解锁时就不用再唤醒别人了 |
| `mutexStarving`（第 2 位） | 处于饥饿模式 |
| 第 3 位及以上 | 等待者的数量 |

**加锁的过程：**
1. **快速路径**：CAS 把 0 改成“已上锁”。没有竞争时，加锁就是这一条原子指令。
2. **自旋**：最多 4 次，条件是多核、GOMAXPROCS > 1、至少还有一个别的 P 在运行、当前 P 的本地队列是空的。也就是说，“锁很可能马上释放，而且我等一下也不耽误别人”时才自旋。
3. **排队**：在信号量上睡眠，等解锁的人唤醒。

**两种模式：**

| | 正常模式 | 饥饿模式 |
|---|---|---|
| 解锁后谁拿到锁 | 被唤醒的等待者和新来的 goroutine 竞争 | 直接交给队头的等待者 |
| 新来的 goroutine | 可以自旋、可以抢 | 不自旋，直接排到队尾 |
| 进入条件 | 默认 | 某个等待者醒来时已经等了超过 1 毫秒，而且锁仍被占用 |
| 退出条件 | | 拿到锁的等待者是队里最后一个，或者它等了不到 1 毫秒 |
| 优点 | 吞吐量高：正在运行的 goroutine 可以连续拿锁，不用切换 | 防止有人一直拿不到锁，控制尾延迟 |

Go 1.24 起，Mutex 的实现移到了 `internal/sync` 包，`sync.Mutex` 只是包了一层，机制没有变。

#### 项目里的例子

> **项目里没有直接体现，但面试常问**：状态字、自旋条件、饥饿模式，这些都在 Mutex 内部，代码里看不到。

项目里用得到的是 Mutex 的这几个性质：
- **logMu** 是一把普通的 Mutex，开启 AOF 时所有写命令都要先拿它（[database/write.go](../../database/write.go) 的 `executeWrite`），保证写进日志的顺序就是修改内存的顺序。
- 写命令持有 logMu 期间要做 fsync，可能要几毫秒。这时等 logMu 的写命令很容易等超过 1 毫秒，锁就会进入饥饿模式，按先来后到的顺序处理。对写入来说，这正好是想要的公平性。

#### 常见追问

**追问 1：可以在一个 goroutine 里加锁，在另一个里解锁吗？**

可以。Go 的 Mutex 不记录是谁加的锁，这也是它不可重入的原因：它分辨不出“又来加锁的是不是同一个人”。不过这样写很难读懂，应该尽量避免。

**追问 2：Go 为什么不提供可重入锁？**

Go 的设计者认为，需要重入通常说明代码结构有问题：一个函数在持有锁时又调用了另一个也要加锁的函数，不变量的边界就说不清了。推荐的做法是拆成两个版本：对外的方法负责加锁，再调用一个“假设调用者已持有锁”的内部函数。

### 八股 2：RWMutex 适合什么场景？为什么读锁不能升级？

#### 一分钟口述版

> 读写锁允许多个读者同时持有，写者独占，适合读多写少、而且读操作本身不是特别短的场景。Go 的 RWMutex 是写者优先的：一旦有写者在等，后来的读者就要排在它后面，防止读者源源不断，写者永远等不到。这带来两个后果。第一，不能在持有读锁时再加一次读锁：如果两次之间有写者来排队，第二次读锁要等写者，写者又要等第一次读锁释放，就死锁了。第二，读锁不能直接升级成写锁：两个读者同时想升级，都要等对方释放读锁，也会死锁。所以要从读变成写，只能先释放读锁，再加写锁；而释放和加锁之间，别人可能已经改过数据了，加上写锁以后必须重新检查一遍。

#### 要点

**实现**（`sync/rwmutex.go`）：

```text
type RWMutex struct {
	w           Mutex        // 写者之间互斥
	writerSem   uint32       // 写者在这里等读者走完
	readerSem   uint32       // 读者在这里等写者走完
	readerCount atomic.Int32 // 读者数量；有写者在等时被减去 2^30，变成负数
	readerWait  atomic.Int32 // 写者还要等多少个读者离开
}
```

- **加读锁**：`readerCount` 加 1。结果是负数，说明有写者在等或正在写，就去 `readerSem` 上睡眠。
- **加写锁**：先拿 `w`，挡住其他写者；再把 `readerCount` 减去 2^30，让它变成负数，宣布“有写者来了”，之后新来的读者都会去睡眠；最后等现有的读者全部离开。
- 所以同时持有读锁的读者最多 2^30 个。

**什么时候不该用 RWMutex**：临界区很短（比如只读一个字段）时，读写锁自身维护计数的开销，可能比普通 Mutex 还大。要不要用，最好用 benchmark 比较一下。

#### 项目里的例子

**1. 每个分片一把 RWMutex。** [database/shard.go](../../database/shard.go) 的 `shard` 里有一把 `mu sync.RWMutex`。GET、LRANGE、TTL 只读数据，拿读锁，同一个分片上的多个读可以同时进行；SET、LPUSH、LPOP、DEL、EXPIRE 要拿写锁。EXISTS 比较特别，它可能要顺手删掉已过期的 key，所以也拿写锁。

**2. lockRead：读锁不能升级时怎么办。** GET 先拿读锁，检查这个 key 有没有过期。如果过期了，就要删掉它，这需要写锁。代码是这样处理的：
1. 释放读锁；
2. 加写锁，**按当前时间重新检查**这个 key 是否过期，过期才删除；
3. 释放写锁，回到循环开头，重新拿读锁再读一遍。

第 2 步为什么要重新检查：在释放读锁和拿到写锁之间，另一个连接可能已经 SET 了同名的 key，设了新的期限。如果不重新检查，直接按第一次看到的“已过期”去删，就会把别人刚写的新值删掉。代码在 [database/expire.go](../../database/expire.go) 的 `lockRead`，本章的代码走读会逐行看。

**3. 多 key 命令也不能对同一个分片加两次锁。** DEL a b，如果 a 和 b 恰好在同一个分片，对这个分片加两次写锁，第二次会永远等第一次释放。所以 `lockKeys` 会先把 key 换算成分片编号，**去重**，再加锁。八股 4 还会讲它为什么要**排序**。

#### 常见追问

**追问 1：如果读的时候发现要写，有没有不释放读锁的办法？**

用 RWMutex 没有。可选的办法：一开始就加写锁（简单，但读也变成串行了）；或者像 lockRead 那样，释放后重新检查。还可以换数据结构，比如读路径完全不删除，只把过期删除交给后台任务。Mini-Redis 选了“释放后重新检查”，因为过期在读路径上是少数情况，大部分 GET 只走读锁。

**追问 2：读写锁会不会让写者饿死？**

Go 的实现不会：有写者在等时，新来的读者会排在它后面。代价就是上面说的，递归加读锁会死锁。

### 八股 3：defer 的规则和开销

#### 一分钟口述版

> defer 把一个函数调用推迟到当前函数返回之前执行。有三条规则：多个 defer 按后进先出的顺序执行；defer 后面那个调用的参数，在执行 defer 语句时就求值了，而不是在真正调用时；defer 可以读取和修改命名返回值，因为 return 语句会先给返回值赋值，再执行 defer。defer 最常见的用法是成对的资源管理：加锁后立刻 defer 解锁，打开文件后立刻 defer 关闭，这样函数从任何地方返回，资源都会被释放；它也是 recover 唯一能生效的地方。关于开销：Go 1.13 把 defer 记录放到了栈上，Go 1.14 引入了开放编码，函数里 defer 不超过 8 个、而且不在循环里时，编译器直接把 defer 的调用内联到每个返回点，开销几乎为零。所以现在一般不需要为了性能而避免 defer。

#### 要点

- **执行时机**：return 语句给返回值赋值 → 按后进先出执行 defer → 函数真正返回。
- **参数求值**：`defer fmt.Println(x)` 立刻求值 x；`defer func() { fmt.Println(x) }()` 闭包里读的是返回时的 x。
- **修改返回值**：只有命名返回值能被 defer 修改。常见用法是在 defer 里给 `err` 加上上下文，或者 recover 后把 panic 转成 error。
- **开放编码的条件**（Go 1.27.1 源码）：
  - defer 个数不超过 8；
  - 不在循环里；
  - 返回语句个数 × defer 个数不超过 15。

  不满足时，退回到在栈上或堆上分配 defer 记录的方式。
- **循环里的 defer** 要等整个函数返回才执行，不是每次迭代结束时执行。在循环里打开文件并 defer 关闭，文件会一直开着直到函数结束。这时应该把循环体抽成一个函数。

#### 项目里的例子

- **加锁后立刻 defer 解锁**，在引擎里随处可见。[database/shard.go](../../database/shard.go) 的 `lockKeys` 返回一个解锁函数，调用者写 `unlock := e.lockKeys(keys, true)` 紧跟着 `defer unlock()`，加了几把锁就解几把，顺序和加锁相反。
- **logMu 只在开启 AOF 时加锁，defer 写在 if 里面**：

  ```go
  if e.log != nil {
  	e.logMu.Lock()
  	defer e.logMu.Unlock()
  }
  ```

  这段在 [database/write.go](../../database/write.go) 的 `executeWrite` 里。defer 属于整个函数，不属于 if 块。这里的 defer 会在 executeWrite 返回时执行，不是在 if 结束时执行。这正是想要的效果：logMu 要一直持有到内存修改完成。

#### 常见追问

**追问：defer 里调用 recover，为什么必须直接写在 defer 的函数里？**

recover 只在“被 defer 直接调用的函数”里生效。在 defer 的函数里再调用一个辅助函数，由辅助函数去调用 recover，是接不住 panic 的。第 06 章细讲。

### 八股 4：死锁是怎样产生的？怎样避免？

#### 一分钟口述版

> 死锁就是几个 goroutine 互相等待对方手里的资源，谁都走不下去。它需要同时满足四个条件：资源互斥；拿着一个资源再去等另一个；资源不能被抢走；等待关系形成了一个环。前三个条件是锁本身的性质，没法破坏，实际能做的是打破“环”：规定一个全局的加锁顺序，所有代码都按这个顺序加锁，就不会出现 A 等 B、B 又等 A 的情况。其他办法还有：缩小锁的范围，持有锁时不调用外部代码；或者用 TryLock、带超时的方式加锁，拿不到就放弃。Go 运行时只能检测“所有 goroutine 都在等”这种全局死锁，会报 `all goroutines are asleep - deadlock!`；只要还有一个 goroutine 能动，比如在等网络连接，局部的死锁它就发现不了。

#### 要点

下面两个 goroutine 按相反的顺序加锁，`Sleep` 保证它们各拿到一把锁以后再去拿另一把：

```go
package main

import (
	"sync"
	"time"
)

func main() {
	var a, b sync.Mutex
	var wg sync.WaitGroup
	wg.Go(func() {
		a.Lock()
		time.Sleep(10 * time.Millisecond)
		b.Lock() // 等 b，而 b 在另一个 goroutine 手里
	})
	wg.Go(func() {
		b.Lock()
		time.Sleep(10 * time.Millisecond)
		a.Lock() // 等 a，而 a 在第一个 goroutine 手里
	})
	wg.Wait()
}

// 运行结果：fatal error: all goroutines are asleep - deadlock!，后面跟着各 goroutine 的堆栈
```

这里运行时能报出来，是因为 main 也在 `Wait` 上等，所有 goroutine 都卡住了。在服务端程序里，总有 goroutine 在等网络连接，运行时不会报，程序只是“卡住不动”。这时可以用 `kill -QUIT`（Linux）让程序打印所有 goroutine 的堆栈，或者用 pprof 的 goroutine profile（第 08 章），看谁卡在哪把锁上。

**运行时什么时候报死锁**：没有 goroutine 能运行，也没有计时器在等着唤醒谁。只要有 goroutine 在等网络或者计时器，就不会报。

#### 项目里的例子

**多 key 命令按分片编号排序后加锁。** `DEL a b` 和 `DEL b a` 同时执行，如果按参数顺序加锁，就和上面的例子一模一样：一个先锁 a 的分片再锁 b 的，另一个反过来。`lockKeys` 把 key 换算成分片编号，去重后从小到大排序，再依次加锁，释放时倒序。不管参数是什么顺序，所有命令加锁的顺序都一样，等待关系不可能成环。代码在 [database/shard.go](../../database/shard.go)。

**logMu 永远在分片锁之前。** 写命令的加锁顺序固定是：logMu → 按编号排序的分片锁（[database/write.go](../../database/write.go) 的 `executeWrite`）。没有任何代码先拿分片锁再拿 logMu，所以这两层之间也不会成环。

[database/engine_test.go](../../database/engine_test.go) 的 `TestConcurrentListAndMultiKeyCommands` 让 8 个 goroutine 同时执行 SET、EXISTS、反序的 DEL 和 LPUSH，检查不丢数据、不卡死。不过测试跑通只能说明这几种时序没出问题，不能证明永远不会死锁；真正的保证来自“全局统一的加锁顺序”这个规则。动手实验 1 会去掉排序，看这个测试怎样卡死。

#### 常见追问

**追问：锁和 channel 怎么选？**

Go 有一句常被引用的话：“不要通过共享内存来通信，而要通过通信来共享内存。”但它不是说锁不好。经验是：**保护一份共享的状态**（缓存、计数器、Mini-Redis 的分片数据）用锁，简单直接；**在 goroutine 之间传递数据或者所有权、通知事件**（生产者消费者、任务分发、停机信号）用 channel。第 07 章会讲 Mini-Redis 改造时为什么去掉了一个不必要的 channel。

### 配角：分片锁的性能数据，以及 Redis 为什么用单线程

**386.9 → 58.1 ns/op 是怎样测出来的。** [database/benchmark_test.go](../../database/benchmark_test.go) 的 `BenchmarkEngine` 先往引擎里写 10000 个 key，每个值 64 字节，然后用 `b.RunParallel` 让 16 个 goroutine（GOMAXPROCS=16）同时随机读写。它比较了三种分片数（1、16、64）和三种负载。下面是第一阶段完成时记录的数据（每格取三次的中位数，单位 ns/op，原始输出在 [docs/performance.md](../performance.md)）：

| 负载 | 1 个分片（相当于一把全局锁） | 16 个分片 | 64 个分片 |
|---|---:|---:|---:|
| 读:写 = 9:1 | 386.90 | 58.11 | 34.70 |
| 纯写 | 361.60 | 109.60 | 68.48 |
| 80% 的请求落在同一个 key 上，读:写 = 1:1 | 381.70 | 394.30 | 405.80 |

怎样读这张表：
- 只有 1 个分片时，所有操作抢同一把锁，大部分时间花在排队上。
- 分片越多，不同 key 落在同一把锁上的机会越小，并行度越高。
- 热点负载下，80% 的请求访问同一个 key，不管分多少片，它们都抢同一个分片的锁，所以分片带不来改善。数字还略差一点，但差距只有几个百分点，不宜过度解读。

这说明分片解决的是**不同 key 之间的锁竞争**，解决不了热点 key。

**换一天再测，数字会变。** 2026-11-10 在同一台机器上，把改造前（31684b7）和改造后（dbd2e9f）的代码交替各跑 4 次，中位数如下：

| 负载 | 分片数 | 改造前 | 改造后 |
|---|---:|---:|---:|
| 读:写 = 9:1 | 1 | 401.1 | 410.5 |
| 读:写 = 9:1 | 16 | 61.7 | 62.2 |
| 读:写 = 9:1 | 64 | 36.9 | 36.6 |
| 纯写 | 1 | 469.9 | 491.8 |
| 纯写 | 16 | 116.2 | 118.6 |
| 纯写 | 64 | 73.7 | 78.5 |
| 热点 | 1 | 620.7 | 585.0 |
| 热点 | 16 | 568.7 | 592.5 |
| 热点 | 64 | 574.0 | 639.1 |

- 两个版本在同一时段的差异，大多在几个百分点以内，而且有的变快、有的变慢，看不出稳定的方向。热点负载本身波动就大，同一格四次测量最多能差 100 多纳秒。每次操作的内存分配次数完全相同。
- 但和上面第一阶段的表比，单分片的纯写和整个热点负载今天都慢了三到六成（读多写少基本没变）。同一时段跑的改造前代码也一样慢，所以不是这次改造造成的。至于为什么比 10 月慢，没有查清：两次之间代码版本不同（10 月之后还改过写路径），运行参数不同（10 月每格 2 秒、跑 3 次，这次每格 1 秒、跑 4 次），机器状态也可能不同。
- 所以比较两个版本的快慢，要在同一时段交替运行；只拿今天的数字和上个月记录的数字比，得不出结论。第 08 章细讲怎样让 benchmark 可信。

**Redis 为什么用单线程执行命令。** Redis 的命令大多是纯内存操作，耗时在微秒级，瓶颈通常是网络 IO，而不是 CPU。单线程执行命令有几个好处：完全不需要锁，每条命令天然是原子的，代码简单，也没有锁竞争和上下文切换的开销。代价是一条慢命令（比如 `KEYS *`）会卡住所有客户端，而且一个实例只能用满一个核，所以生产环境常常在一台机器上跑多个实例，或者用集群。Redis 6.0 起可以用多个线程做网络读写，但命令的执行仍然是单线程。

Mini-Redis 选择多个 goroutine 并发执行命令，是为了练习 Go 的并发控制：分片锁、加锁顺序、读锁不能升级，这些问题在单线程模型里根本不会出现。

## 关键设计与为什么

**1. 分片锁，而不是一把全局锁。**
- 为什么：不同 key 的命令可以同时执行。基准测试里，读多写少的负载从三百多纳秒降到几十纳秒。
- 代价：多 key 命令要同时拿多把锁，必须规定加锁顺序；热点 key 帮不上忙。

**2. 全局统一的加锁顺序：先 `logMu`，再按分片编号从小到大。**
- 这是避免死锁的唯一保证。测试只能发现碰巧撞上的死锁，规则才能排除所有情况。

**3. 读路径先拿读锁，过期了再“放读锁、加写锁、重新检查”。**
- 为什么：绝大多数 GET 读到的 key 没有过期，只拿读锁，同一个分片上的读可以并行。
- 放弃了什么：GET 一律拿写锁会简单得多，但同一个分片上的读就全部串行了。

**4. 刷盘期间一直持有锁。**
- 为什么：日志落盘以后才改内存，而且日志顺序要和内存顺序一致，所以 `logMu` 和分片锁要一直拿到内存改完。
- 代价：开启 AOF 后，有实际效果的写命令完全串行，每条都要等一次 fsync。真实的 Redis 开启 AOF 时，默认每秒刷一次盘（`appendfsync everysec`），用“最多丢一秒的数据”换吞吐量；Mini-Redis 选择每条都刷，不丢已确认的写。第 06 章细讲。

## 常见误区

- **复制了含锁的结构体。** 值接收者、按值传参、把结构体存进 map 再取出来，都会复制锁。用 `go vet` 检查。
- **在持有锁时调用外部代码或者做 IO。** 锁持有时间会变长，还可能因为外部代码也要加锁而死锁。Mini-Redis 在持锁时做 fsync 是一个有意的取舍，第 06 章会讲为什么，以及代价是什么。
- **递归加读锁。** 中间来一个写者就会死锁。
- **释放读锁再加写锁之后，不重新检查。** 中间别人可能已经改过数据了。
- **在循环里 defer 解锁。** defer 要等整个函数返回才执行，第二次循环加锁就死锁了。
- **以为运行时能发现所有死锁。** 它只能发现“所有 goroutine 都在等”的情况。

## 自测

**1. `lockKeys` 为什么要去重？为什么要排序？少了哪一步会出什么事？**

<details><summary>答案</summary>

去重：两个 key 可能落在同一个分片，同一把锁加两次，第二次会永远等第一次释放（Mutex 不可重入）。排序：所有命令按同一个顺序加锁，等待关系不会成环；不排序时，参数顺序相反的两条多 key 命令并发执行会互相等待。动手实验 1 里卡死的是 `EXISTS key other` 和 `DEL other key`：前者先锁 key 的分片再锁 other 的，后者反过来。（换成两条参数相反的 DEL，在开启 AOF 时它们会先在 `logMu` 上排队，反而不会同时去抢分片锁。）

</details>

**2. `lockRead` 发现 key 过期后，为什么不能直接把读锁换成写锁？加上写锁以后为什么要重新检查？**

<details><summary>答案</summary>

RWMutex 没有“升级”操作：持有读锁再加写锁，写锁要等所有读者离开，包括自己，就死锁了。所以只能先放读锁、再加写锁。两步之间别的连接可能已经写了一个新值，所以加上写锁后要按当前时间重新检查，过期才删。

</details>

**3. EXISTS 只是读，为什么拿写锁？**

<details><summary>答案</summary>

EXISTS 判断存在时，会顺手删掉已经过期的 key（`purgeExpired`），删除要写锁。它涉及多个 key，所以用 `lockKeys` 按顺序一次锁住所有相关分片。

</details>

**4. 开启 AOF 以后，16 个分片对写命令还有帮助吗？**

<details><summary>答案</summary>

几乎没有。所有写命令都先拿全局的 `logMu`，排成一队写日志、刷盘，分片带来的写并行没有了。分片对读命令仍然有用：读不拿 `logMu`，不同分片的读可以同时进行。

</details>

**5. 基准测试的热点负载下，为什么 64 个分片并不比 1 个快？**

<details><summary>答案</summary>

80% 的请求访问同一个 key，这些请求都落在同一个分片上，抢的是同一把锁。分片解决的是不同 key 之间的竞争，解决不了同一个 key 上的竞争。

</details>

**6. 下面这段代码里，`logMu` 是在什么时候解锁的？**

```text
if e.log != nil {
	e.logMu.Lock()
	defer e.logMu.Unlock()
}
```

<details><summary>答案</summary>

在 `executeWrite` 返回时。defer 属于整个函数，不属于 if 块，所以 logMu 一直持有到写日志、改内存都完成之后。

</details>
